# 学習方針

このノートブックで、何をどの順に学ぶかと、ノート・Snippet をどう書くかの約束をまとめる。

## このノートで使う用語

| 用語 | 意味 |
|---|---|
| 状態 | timeline の状態。Stop / Play / Pause の3つがある |
| バックエンド | Core Experimental API がデータを読み書きする経路。usd / usdrt / fabric / tensor / simstate がある |
| view | `omni.physics.tensors` が提供するオブジェクトで、実行中の物理エンジンの内部オブジェクト群をまとめて読み書きする窓口 |
| 物理ステップ | 物理エンジンが物理の状態を刻み幅 h 秒だけ進める1回分の計算 |
| Snippet | `snippets/` に置いた、Script Editor にそのまま貼って実行できる観測用の Python ファイル |
| 環境指紋 | env_fingerprint が出力する、設定値・拡張の有効状態・現在の状態の一覧 |
| ベクトル化 | たくさんの要素への同じ計算を、Python の for で1個ずつ回さずに、配列全体への1回の操作として書くこと |

ほかの用語の定義は [用語集](../01_用語と概念/01_用語集.md) にまとめている。

## 1. 目的

Isaac Sim 6.2.0 で、状態（Stop / Play / Pause）とバックエンド（usd / usdrt / fabric / tensor）の組み合わせごとに、どの API がなぜ使えるのか、どれだけの時間がかかるのかを、観測できる Snippet とノートで確かめながら学ぶ。分かったことは、ソースか実測で確かめた事実だけをノートに書く。

## 2. 学ぶ順序

前半で観測の道具をそろえ、後半でその道具を使って各バックエンドを調べる。道具がないまま後半に進むと、結果が正しいかを確かめられないためである。

| 順 | 段階 | やること | 使うノート・Snippet |
|---|---|---|---|
| 1 | 言葉をそろえる | 用語、view、use_backend の範囲、旧 Core API との対応を知る | [用語と概念](../01_用語と概念/00_MOC-用語と概念.md) |
| 2 | 環境指紋 | どの設定の下で実験しているかを記録する。状態によって変わる設定を知る | [env_fingerprint](../05_観測Snippet/01_env_fingerprint.md)、[設定一覧](../04_設定/01_設定一覧.md) |
| 3 | 状態と物理ステップ | Play / Pause / Stop と物理ステップの関係、ウォームアップ、時計のずれを数値で確かめる | [時間と物理ステップ](../03_時間と物理ステップ/01_時間と物理ステップ.md)、[step_probe](../05_観測Snippet/02_step_probe.md)、[clock_probe](../05_観測Snippet/03_clock_probe.md) |
| 4 | 計測の基準 | 計測そのもののオーバーヘッドと、重い処理の見つけ方を知る | [bench_probe](../05_観測Snippet/04_bench_probe.md)、[重い処理と軽くする方法](../05_観測Snippet/08_重い処理と軽くする方法.md) |
| 5 | バックエンドの選ばれ方 | 候補リスト、tensor 専用のメソッド、フォールバック、strict を知る | [バックエンド選択の仕組み](../02_バックエンド選択の仕組み/01_バックエンド選択の仕組み.md)、[supported_backends](../05_観測Snippet/09_supported_backends.md)、[backend_spy](../05_観測Snippet/06_backend_spy.md)、[strict_backend](../05_観測Snippet/07_strict_backend.md) |
| 6 | 物理の出力先と読める値 | USD・Fabric・どちらにも書かない、の3通りで、どの経路が最新の値を返すかを確かめる | [pose_freshness_probe](../05_観測Snippet/05_pose_freshness_probe.md) |
| 7 | tensor と Stop のままの物理 | view が Play で作られ Stop で無効になること、Stop のまま物理を準備して手動ステップで使う方法を確かめる | [lab_parts](../05_観測Snippet/10_lab_parts.md) の「Stop のまま物理を使う」 |
| 8 | ベクトル化の書き方 | 下の「3. for を使わない書き方を学ぶ順序」を進め、たくさんのプリムを1回の呼び出しで扱えるようにする | [重い処理と軽くする方法](../05_観測Snippet/08_重い処理と軽くする方法.md) の項目4・5 |

## 3. for を使わない書き方を学ぶ順序

Core Experimental API のラッパーは、たくさんのプリムを1つのラッパーで受け持ち、値を（プリムの数, 3）のような配列でまとめて受け渡す。fabric と tensor の経路は、この配列を1回の処理でまとめて扱うので速い（1000 個の姿勢の読み出しで、usd の Python ループ 24.7 ms に対し、fabric 0.24 ms、tensor 0.15 ms。実測）。この速さを自分のコードでも失わないためには、配列を1個ずつ for で回さずに、配列全体への操作として書く必要がある。

| 順 | 学ぶもの | 何を学ぶか | 使う場面 |
|---|---|---|---|
| 1 | NumPy | 配列の形（shape）、ブロードキャスト（形の違う配列どうしの計算）、スライス、真偽値の配列で選ぶ（マスク）、インデックスの配列で選ぶ（fancy indexing） | CPU で値を作る・調べる。考え方の土台になる |
| 2 | Warp の配列 | `wp.array` の作り方、`device`（cpu / cuda）、`.numpy()` と `wp.from_numpy()`、`wp.to_torch()` | ラッパーの戻り値はすべて `wp.array` である |
| 3 | Warp のカーネル | `@wp.kernel` で関数を書き、`wp.launch(dim=要素数)` で要素ごとに並列に実行する。fabric の経路の中身も Warp のカーネルである | GPU のまま計算したいとき |
| 4 | PyTorch のテンソル | `torch.Tensor` の演算、`device` | Isaac Lab を使うとき（Isaac Lab はテンソルで受け渡す） |

選ぶときの基準は、データがどこ（CPU か GPU か）にあるかと、写す費用である。

| データの置き場所 | `.numpy()` を呼んだとき | 向いている道具 |
|---|---|---|
| CPU（GUI の既定。`/physics/suppressReadback = false` のときはここになる） | 写さずに同じメモリを見る（返った NumPy 配列を書き換えると、元の `wp.array` も変わった。実測） | NumPy で十分。写す費用はかからない |
| GPU（`/physics/suppressReadback = true` の構成） | GPU から CPU へ写す（1000 個の姿勢で約 90 µs。実測） | GPU のまま計算するなら Warp のカーネルか PyTorch。`wp.to_torch()` は写さずに同じメモリを見る |

最初は NumPy で「配列全体への操作として書く」考え方を身につけ、Isaac Sim の値は `wp.array` で受け取って `.numpy()` で NumPy に渡すのがよい。GUI の既定ではデータは CPU にあるので、この変換に費用はかからない。GPU の構成で大量のデータを扱うようになってから、Warp のカーネルか PyTorch に進む。

## 4. ノートの書き方

- 前から順に読めば理解できる順序で書く。後ろに出てくるものを参照するときは、どこにあるかを明記する（Snippet のノートでは「上の『コード』の節の 〇〇.py（全文）を実行する」と書く）。
- 主語と述語をはっきり書く。「差」と書くときは、何から何を引いた差かを書く。
- 確かめた事実だけを書く。表記なしは公式ドキュメントかソースで確認した事実、「（実測）」は Isaac Sim を動かして測った結果である。推論や未確認のまま知識として書かない。分からないことは、確かめてから書く。
- 最終版だけを書く。「以前はこう書いていた」「〇日に直した」のような編集の経緯は書かない。経緯は、変更前の版を残したフォルダで見る（下の「6. 変更のしかた」）。測った日（「2026-11-09 に実測」など）は、値がいつの環境のものかを示すので書く。
- 挙動に影響する操作や設定は、そのノートの中に、やり方（そのまま実行できるコード）まで書く。ほかのノートに書いてあっても省かない。
- 細かく分けすぎない。1つの話題は1つのノートにまとめ、目次（MOC）だけのノートは、ノートが3つ以上あるフォルダにだけ置く。
- 設定の一覧は、表ではなく、コメント付きのコードで書く（そのまま実行すれば今の値が表示され、`#` を外せば変えられる形）。
- 関数とクラスは、コードブロックの外でも完全修飾名で書き、各ノートの末尾の「このノートに出てくる API の import」に import 文をまとめる。

## 5. Snippet の書き方

### 解説ノートの構成

Snippet の解説ノートは、次の順に書く。

| 節 | 書くこと |
|---|---|
| 目的・仕組み | 何を確かめるか。使っている API がどう動くか（ソースの抜粋） |
| メタ情報 | 有効な状態、使うバックエンド、書き込みが届く先、他のバックエンドから見えるタイミング |
| コード | py ファイルと同じ全文 |
| 観測手順と期待される出力 | どの順にボタンを押し、どのコードを実行するか。何が出れば仮説どおりか（実測した出力を載せる） |
| 手順をコードで自動実行する | Play / Pause / Stop をコードで切り替えて、手順をまとめて行うコード |
| 期待と違ったときに疑う箇所 | 結果に影響しうる設定と、その確かめ方 |
| 結果 | 自分で実行した出力と、その考察 |

### コードの書き方

- Script Editor にそのまま貼って実行できる形にする。すべての行に、何をしているかのコメントを付ける。
- 関数の引数や変数には、用途の分かる名前を付ける（`n`・`fn`・`e` のような1〜2文字の名前にしない）。
- 再実行したときにコールバックが二重に登録されないよう、登録した ID を `builtins` に保存し、次の実行の冒頭で解除する。
- 結果を左右する設定がある場合は、その設定の値を Snippet 自身が表示する。必要なら、設定を切り替える変数（`OUTPUT_MODE` など）を Snippet に持たせる。
- 何度も使う処理は [lab_parts](../05_観測Snippet/10_lab_parts.md) の部品を使うか、部品として足す。
- Play / Pause / Stop をコードで行うときは、`omni.timeline` の `play()` などを呼んだ後、`async` の関数の中で `await omni.kit.app.get_app().next_update_async()` を使って更新を待つ（`play()` などは次の更新で反映される。`commit()` を呼ぶとその場で反映される。実測）。

### メタ情報と環境指紋

メタ情報の4項目は、[設定一覧](../04_設定/01_設定一覧.md) の値が変わると成り立たなくなることがある。そのため、観測結果を記録するときは、[env_fingerprint](../05_観測Snippet/01_env_fingerprint.md) の出力（環境指紋）を一緒に残す。

## 6. 変更のしかた

- 変更する前に、ノートブック全体を `C:\isaacsim-6.2.0\CodeByClaude\isaac-sim-backend-lab_old\` の下に、日付と内容の分かる名前のフォルダごとコピーして残す。WinMerge などで、変更前と変更後を比べられるようにするためである。
- py ファイルとノートのコードが食い違った場合は、ノートの側を正とし、py ファイルをノートに合わせる。
- Snippet は、変更前の版を新しい名前（`_v2` など）で残さない。最終版だけを置き、変更前の版は上のフォルダで見る。

## 7. 事実を確かめる方法

| 方法 | 使う場面 | やり方 |
|---|---|---|
| ソースを読む | API の中身、設定がいつ読まれるか | Isaac Sim のソース（`C:\isaac\IsaacSim\source`）、omni.physx のソース（`C:\isaac\src\PhysX-omni-110.3`）。設定がどこで読まれるかは [lab_parts](../05_観測Snippet/10_lab_parts.md) の `find_setting_usages` で探せる |
| GUI で実行する | 自分の環境での値、Script Editor のログ欄が関わるもの | Snippet を Script Editor で実行し、出力を「結果」の節に貼る |
| ヘッドレスで実測する | 状態を変えながら多くの条件を測るもの | `python.bat` から `isaacsim.SimulationApp` を `apps\isaacsim.exp.full.kit`（GUI と同じ構成）で起動し、ステージを作って測る。各フォルダの `measurements/` に、スクリプトと生データ（jsonl）を置く |
| ノートのコードを検証する | ノートに載せたコードが動くか | ヘッドレスで、Script Editor と同じ実行経路（`omni.kit.app.get_app().get_python_scripting().execute_string()`）でコードブロックを実行し、標準エラーに何も出ないことを確かめる |
