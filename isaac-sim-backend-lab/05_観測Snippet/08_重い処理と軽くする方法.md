# 重い処理と軽くする方法

[bench_probe](04_bench_probe.md) の派生ノートである。Isaac Sim で Python から操作するときに時間がかかる処理を挙げ、項目ごとに次の6つを書く。

1. なぜ重いか
2. 重さを確かめるコード
3. 結果の記入欄（自分の GUI で測った値を書く）
4. 重い処理をなくす方法
5. なくした後に軽くなったことを確かめるコード
6. 結果の記入欄

記入欄の横の「参考」は、2026-11-09 にヘッドレス（GUI と同じ `isaacsim.exp.full.kit`、RTX 3060）で測った値である。GUI では描画やウィンドウの処理が加わるので、値は変わる。

## このノートで使う用語

| 用語 | 意味 |
|---|---|
| 状態 | timeline の状態。Stop / Play / Pause の3つがある |
| バックエンド | Core Experimental API がデータを読み書きする経路。usd / usdrt / fabric / tensor がある |
| ラッパー | Core Experimental API の `isaacsim.core.experimental.prims.XformPrim`・`isaacsim.core.experimental.prims.RigidPrim` などのクラス。1つのラッパーが1個以上のプリムを受け持つ |
| 更新 | メインループの1回分の反復。`omni.kit.app.get_app().update()` の1回にあたる |
| 中央値 | 何回も測った値を小さい順に並べたときの真ん中の値。たまに大きく外れる回の影響を受けにくい |
| µs | マイクロ秒。1 ms（ミリ秒）の 1000 分の 1 |

ほかの用語の定義は [用語集](../01_用語と概念/01_用語集.md) にまとめている。

## まとめ

| 項目  | 重い処理                          | 軽くする方法                 | 参考（ヘッドレスで実測）                                                 |
| --- | ----------------------------- | ---------------------- | ------------------------------------------------------------ |
| 1   | Script Editor で print を1行ずつ呼ぶ | 行をまとめて1回の print で出す    | 1行ずつ 13.3 µs/行 → まとめて 0.35 µs/行（GUI では 1行ずつ 122 µs/行）        |
| 2   | Isaac Sim 自身のログ出力             | ログレベルを上げる              | Play 中は 300 回の更新でログが 0 バイトで、ログレベルを上げても更新時間は変わらなかった（重い処理ではない） |
| 3   | ラッパーを呼ぶたびに作る                  | 1回作って使い回す              | 206 µs → 97 µs                                               |
| 4   | usd / usdrt でたくさんのプリムの姿勢を読む   | fabric か tensor で読む    | 1000 個で 24.7 ms → fabric 0.24 ms、tensor 0.15 ms              |
| 5   | プリムを1個ずつループで書く                | まとめて1回で書く              | 100 個で 11.5 ms → 0.089 ms                                    |
| 6   | 物理の計算結果を毎ステップ USD に書き戻す       | Fabric へ書く、またはどこにも書かない | 剛体 1000 個で 1回の更新 66 ms → 8.4 ms（Fabric）、6.2 ms（書かない）         |
| 7   | GPU の配列を CPU に写す              | 写さずに GPU のまま使う         | 1000 個で 240 µs → 331 µs（写すと +90 µs。小さい）                      |

## 共通：時間を測る関数

各項目の確認コードは、それぞれ単独で Script Editor に貼って実行できるように、次の関数を先頭に含めている（項目4の後半・5・7は、項目4のコードで作った `paths` などの変数と、この関数を使う。Script Editor で続けて実行したコードは、同じ名前空間で動くので、前に実行したコードの変数をそのまま使える。ヘッドレスで、Script Editor と同じ実行経路で確かめた）。`action` を `repeat_count` 回呼び、1回あたりの所要時間の中央値をマイクロ秒で返す。

```python
# 1回あたりの所要時間の中央値を µs で返す関数（各確認コードの先頭に同じものを入れている）
import statistics  # 中央値を計算する
import time  # 高分解能タイマー perf_counter を使う


def time_per_call_us(action, repeat_count=100):
    """action を repeat_count 回呼び、1回あたりの所要時間の中央値を µs で返す。"""
    samples = []  # 1回ごとの所要時間（秒）
    for _ in range(repeat_count):  # repeat_count 回くり返す
        start = time.perf_counter()  # 開始時刻
        action()  # 計る処理を1回呼ぶ
        samples.append(time.perf_counter() - start)  # 経過時間を記録する
    return statistics.median(samples) * 1e6  # 中央値を µs にして返す
```

## 1. Script Editor の print

### なぜ重いか

Script Editor で実行したコードの print は、1回ごとに1件のイベントとして Script Editor のログ欄に送られる（引数の数によらず1回の print で1件。ヘッドレスで数えた）。ログ欄（`omni.kit.window.script_editor` の `log_view.py` の `LogModel`）は、1件受け取るたびにその行を一覧に足し、表示用のツリーに作り直させる。ソースのコメントにも「行数が多いと、作り直しのたびに時間がかかり UI が固まる」と書かれている。ログ欄は最大 1000 行を保ち（設定 `/exts/omni.kit.window.script_editor/maxLogLines`、既定 1000）、2000 行を超えると古い行を捨てる。

### 重さを確かめるコード

Script Editor に貼って実行するコード（ファイルではない。どの状態でもよい）
```python
# Script Editor で print を1行ずつ呼んだときの、1行あたりの時間を測る
import statistics  # 中央値を計算する
import time  # 高分解能タイマー perf_counter を使う


def time_per_call_us(action, repeat_count=100):
    """action を repeat_count 回呼び、1回あたりの所要時間の中央値を µs で返す。"""
    samples = []  # 1回ごとの所要時間（秒）
    for _ in range(repeat_count):  # repeat_count 回くり返す
        start = time.perf_counter()  # 開始時刻
        action()  # 計る処理を1回呼ぶ
        samples.append(time.perf_counter() - start)  # 経過時間を記録する
    return statistics.median(samples) * 1e6  # 中央値を µs にして返す


one_line_us = time_per_call_us(lambda: print("line"), repeat_count=200)  # print を1行ずつ200回呼ぶ
print(f"[RESULT] print 1行ずつ: {one_line_us:.1f} us/行")  # 結果を表示する
```

### 結果

| 条件 | 1行あたり | 参考 |
|---|---|---|
| ログ欄を右クリック → Clear した直後に実行 | ＿＿＿ µs | — |
| ログ欄に 1000 行ほど溜まった状態で実行 | ＿＿＿ µs | GUI で 122 µs（[bench_probe](04_bench_probe.md) の補足の結果）。ヘッドレス（ログ欄を表示しない）では 13.3 µs |

### なくす方法

1. **行をまとめて1回の print で出す。** 行をリストに貯めておき、最後に `print("\n".join(行のリスト))` で出す。ログ欄に送られるイベントは1件になる（ヘッドレスで数えた）。観測用の Snippet のように、更新ごとに1行出すものは、決めた回数分を貯めてから出す。
2. **ログ欄を Clear してから実行する。** ログ欄を右クリックして Clear を選ぶと、溜まっていた行が消える。
3. **ログ欄の最大行数を小さくする。** `/exts/omni.kit.window.script_editor/maxLogLines` は、ログ欄が作られたときに1回だけ読まれる（ソース）。起動時のオプション `--/exts/omni.kit.window.script_editor/maxLogLines=200` で指定する。
4. **そもそも print しない。** 観測値をリストや辞書に貯めて、必要なときだけ表示する。

### 軽くなったことを確かめるコード

Script Editor に貼って実行するコード（ファイルではない。どの状態でもよい）
```python
# 100行を1回の print にまとめたときの、1行あたりの時間を測る
import statistics  # 中央値を計算する
import time  # 高分解能タイマー perf_counter を使う


def time_per_call_us(action, repeat_count=100):
    """action を repeat_count 回呼び、1回あたりの所要時間の中央値を µs で返す。"""
    samples = []  # 1回ごとの所要時間（秒）
    for _ in range(repeat_count):  # repeat_count 回くり返す
        start = time.perf_counter()  # 開始時刻
        action()  # 計る処理を1回呼ぶ
        samples.append(time.perf_counter() - start)  # 経過時間を記録する
    return statistics.median(samples) * 1e6  # 中央値を µs にして返す


LINES_PER_PRINT = 100  # 1回の print にまとめる行数
lines = [f"line {index}" for index in range(LINES_PER_PRINT)]  # 出したい行を先にリストに貯めておく
batched_us = time_per_call_us(lambda: print("\n".join(lines)), repeat_count=20)  # 100行をまとめた print を20回呼ぶ
print(f"[RESULT] 100行を1回にまとめた print: {batched_us:.1f} us/回 = {batched_us / LINES_PER_PRINT:.2f} us/行")  # 1行あたりに直して表示する
```

### 結果

| 条件 | 1行あたり | 参考 |
|---|---|---|
| 100行を1回の print にまとめる（Clear した直後） | ＿＿＿ µs | ヘッドレスで 0.35 µs（1回 34.8 µs） |
| 100行を1回の print にまとめる（1000 行溜まった後） | ＿＿＿ µs | — |

## 2. Isaac Sim 自身のログ出力

### なぜ重いと考えたか、実際にはどうか

Isaac Sim は起動時やステージを開いたときに、Console ウィンドウとログファイルに多くの行を出す。Play 中もログを出し続けているなら、ログの量を減らすと更新が速くなるはずだ、という考えである。

実測では、Play 中のログ出力は重い処理ではなかった。剛体 100 個を落としている Play 中の 300 回の更新で、ログファイルは 1 バイトも増えなかった。ログレベルを Error に上げても、1回の更新の中央値は 13.14 ms と 13.06 ms で、差は計測誤差の範囲だった。ログを出す関数の費用も小さい（`carb.log_warn` で 1行 14.6 µs、既定のログレベルでは出力されない `carb.log_info` で 5.1 µs）。ログが更新を遅くするのは、自分のコードや拡張機能が毎回の更新でログを出している場合だけである。それは、次のコードでログファイルが増え続けることで分かる。

### 重さを確かめるコード

Script Editor に貼って実行するコード（ファイルではない。Play 中に実行する）
```python
# Play 中の300回の更新で、ログファイルが何バイト増えるかと、1回の更新の時間を測る
import asyncio  # async の関数を Kit のイベントループで走らせる
import os  # ログファイルの大きさを読む
import statistics  # 中央値を計算する
import time  # 高分解能タイマー perf_counter を使う

import carb.settings  # ログファイルの場所を読む
import omni.kit.app  # メインループの更新を待つ

UPDATE_COUNT = 300  # 何回分の更新を測るか


async def measure_log_volume() -> None:
    """UPDATE_COUNT 回の更新の前後でログファイルの大きさを比べ、更新1回の時間も測る。"""
    log_path = carb.settings.get_settings().get("/log/file")  # ログファイルの場所
    app = omni.kit.app.get_app()  # 更新を待つためのアプリのインスタンス
    size_before = os.path.getsize(log_path)  # 測る前の大きさ
    durations = []  # 更新1回ごとの時間（秒）
    previous = time.perf_counter()  # 前の更新が終わった時刻
    for _ in range(UPDATE_COUNT):  # UPDATE_COUNT 回の更新を待つ
        await app.next_update_async()  # 更新を1回待つ
        now = time.perf_counter()  # 今の時刻
        durations.append(now - previous)  # 更新1回分の時間を記録する
        previous = now  # 次の基準にする
    size_after = os.path.getsize(log_path)  # 測った後の大きさ
    print(f"[RESULT] ログ {size_after - size_before} バイト増加 / 更新 {UPDATE_COUNT} 回、更新1回の中央値 {statistics.median(durations) * 1000:.2f} ms")  # 結果を表示する
    print(f"[INFO] ログファイル: {log_path}")  # どのファイルを見たかを表示する


asyncio.ensure_future(measure_log_volume())  # Kit のイベントループで走らせる（この行はすぐに戻る）
```

### 結果

| 条件 | 増えたバイト数 | 更新1回の中央値 | 参考 |
|---|---|---|---|
| 既定のログレベル | ＿＿＿ バイト | ＿＿＿ ms | 0 バイト、13.14 ms（剛体 100 個、待ちを外した構成） |

### なくす方法（ログが増え続けている場合）

ログの出力先ごとに、出す最低のレベルを設定で変えられる。値は `"verbose"`、`"info"`、`"warn"`、`"error"`、`"fatal"` のどれかである。GUI の既定は `/log/level = Info`、`/log/outputStreamLevel = Warning`（端末）、`/log/fileLogLevel = Info`（ログファイル）だった。

Script Editor に貼って実行するコード（ファイルではない）
```python
# ログを Error 以上だけにする（再起動すると元に戻る）
import carb.settings  # Kit の設定を読み書きする

settings = carb.settings.get_settings()  # 設定ストアを取得する
settings.set_string("/log/level", "error")  # ログ全体の最低レベル
settings.set_string("/log/outputStreamLevel", "error")  # 端末（標準出力）に出す最低レベル
settings.set_string("/log/fileLogLevel", "error")  # ログファイルに書く最低レベル
```

### 軽くなったことを確かめる

上のコードでログレベルを変えてから、「重さを確かめるコード」をもう一度実行する。

| 条件 | 増えたバイト数 | 更新1回の中央値 | 参考 |
|---|---|---|---|
| ログレベルを error にした後 | ＿＿＿ バイト | ＿＿＿ ms | 0 バイト、13.06 ms |

## 3. ラッパーを呼ぶたびに作る

### なぜ重いか

`isaacsim.core.experimental.prims.XformPrim` などのラッパーは、作るときにパスを解決し、プリムの有効性を確かめ、内部の準備をする。更新ごとの処理の中で毎回 `XformPrim(パス)` と書くと、そのたびにこの準備が走る。

### 重さを確かめるコードと、なくした後を確かめるコード

作るたびに読む場合と、作っておいたラッパーで読む場合を、続けて測る。

Script Editor に貼って実行するコード（ファイルではない。/World/Cube があるステージで実行する）
```python
# ラッパーを毎回作って読む場合と、1回作って使い回す場合の時間を比べる
import statistics  # 中央値を計算する
import time  # 高分解能タイマー perf_counter を使う

from isaacsim.core.experimental.prims import XformPrim  # Xform のラッパー


def time_per_call_us(action, repeat_count=100):
    """action を repeat_count 回呼び、1回あたりの所要時間の中央値を µs で返す。"""
    samples = []  # 1回ごとの所要時間（秒）
    for _ in range(repeat_count):  # repeat_count 回くり返す
        start = time.perf_counter()  # 開始時刻
        action()  # 計る処理を1回呼ぶ
        samples.append(time.perf_counter() - start)  # 経過時間を記録する
    return statistics.median(samples) * 1e6  # 中央値を µs にして返す


PRIM_PATH = "/World/Cube"  # 読むプリムのパス（自分のシーンに合わせて書き換える）
create_each_time_us = time_per_call_us(lambda: XformPrim(PRIM_PATH).get_world_poses(), repeat_count=50)  # 毎回作って読む
xform_once = XformPrim(PRIM_PATH)  # 1回だけ作る
reuse_us = time_per_call_us(lambda: xform_once.get_world_poses(), repeat_count=200)  # 作っておいたもので読む
print(f"[RESULT] 毎回作る: {create_each_time_us:.1f} us、使い回す: {reuse_us:.1f} us")  # 結果を表示する
```

### 結果

| 条件 | 1回あたり | 参考 |
|---|---|---|
| 毎回作って読む | ＿＿＿ µs | 206 µs |
| 1回作って使い回す | ＿＿＿ µs | 97 µs |

### なくす方法

ラッパーは、観測や制御を始める前に1回だけ作り、変数や `builtins` に保存して使い回す。ラッパーは Play のたびに内部の view を作り直すので（[backend_spy](06_backend_spy.md) の期待される出力）、Stop 中に作ったラッパーを Play 中にそのまま使ってよい。ただし、ステージを開き直したときは作り直す。

## 4. usd / usdrt でたくさんのプリムの姿勢を読む

### なぜ重いか

`isaacsim.core.experimental.prims.XformPrim.get_world_poses()` の usd と usdrt の経路は、プリム1個ごとに Python のループで変換行列を読む（[複数プリム対応とPythonループの有無](../01_用語と概念/05_複数プリム対応とPythonループの有無.md)）。時間はプリムの数 N に比例して伸びる。fabric の経路は Warp のカーネルで N 個をまとめて処理し、tensor の経路は子の view から N 個分を1回で受け取る。

### 重さを確かめるコード

Script Editor に貼って実行するコード（ファイルではない。Stop 中に実行する。/World/HeavyTest の下に Cube を CUBE_COUNT 個作る）
```python
# Cube を CUBE_COUNT 個作り、XformPrim.get_world_poses を usd と usdrt で測る
import statistics  # 中央値を計算する
import time  # 高分解能タイマー perf_counter を使う

import isaacsim.core.experimental.utils.backend as backend_utils  # バックエンドを指定する use_backend を使う
import omni.usd  # 開いているステージを取得する
from isaacsim.core.experimental.prims import XformPrim  # Xform のラッパー
from pxr import Gf, UsdGeom, UsdPhysics  # USD のプリムと物理の API


def time_per_call_us(action, repeat_count=100):
    """action を repeat_count 回呼び、1回あたりの所要時間の中央値を µs で返す。"""
    samples = []  # 1回ごとの所要時間（秒）
    for _ in range(repeat_count):  # repeat_count 回くり返す
        start = time.perf_counter()  # 開始時刻
        action()  # 計る処理を1回呼ぶ
        samples.append(time.perf_counter() - start)  # 経過時間を記録する
    return statistics.median(samples) * 1e6  # 中央値を µs にして返す


CUBE_COUNT = 1000  # 作る Cube の数
stage = omni.usd.get_context().get_stage()  # 開いているステージ
paths = []  # 作った Cube のパス
for index in range(CUBE_COUNT):  # CUBE_COUNT 個作る
    path = f"/World/HeavyTest/c_{index}"  # Cube のパス
    cube = UsdGeom.Cube.Define(stage, path)  # Cube を作る
    cube.CreateSizeAttr(0.1)  # 一辺 0.1 m
    UsdGeom.XformCommonAPI(cube).SetTranslate(Gf.Vec3d(0.3 * (index % 32), 0.3 * (index // 32), 5.0))  # 格子状に並べる
    UsdPhysics.RigidBodyAPI.Apply(cube.GetPrim())  # 剛体にする（項目4・5・6で使う）
    UsdPhysics.CollisionAPI.Apply(cube.GetPrim())  # コライダーを付ける
    paths.append(path)  # パスを記録する
xform = XformPrim(paths)  # CUBE_COUNT 個をまとめて受け持つラッパー
for backend in ("usd", "usdrt"):  # Python のループがある2つの経路

    def read_with(backend_name=backend):
        """指定したバックエンドで全部の姿勢を読む。"""
        with backend_utils.use_backend(backend_name):  # バックエンドを指定する
            xform.get_world_poses()  # 全部の姿勢を読む

    print(f"[RESULT] N={CUBE_COUNT} {backend}: {time_per_call_us(read_with, repeat_count=20):.1f} us")  # 結果を表示する
```

### 結果

| N    | usd    | usdrt  | 参考（usd / usdrt）                                            |
| ---- | ------ | ------ | ---------------------------------------------------------- |
| 1000 | ＿＿＿ µs | ＿＿＿ µs | 24745 µs / 22512 µs（Play 中）<br>22476 µs / 22413 µs（Stop 中） |

### なくす方法

- 物理を持たない Xform の姿勢は、`with isaacsim.core.experimental.utils.backend.use_backend("fabric"):` の中で読む（Fabric Scene Delegate が有効な場合）。
- 剛体の姿勢は、Play 中に `isaacsim.core.experimental.prims.RigidPrim` で読む（tensor が選ばれる）。
- N が数個しかない場合は、usd のままのほうが速い（N = 1 で usd 100 µs、fabric 208 µs。fabric は呼ぶたびに Fabric の階層を更新する固定費がある）。

### 軽くなったことを確かめるコード

Script Editor に貼って実行するコード（ファイルではない。上のコードを実行した後に実行する。RigidPrim の行は Play 中に実行する）
```python
# 上で作った xform と paths を使い、fabric と tensor（RigidPrim）で測る
from isaacsim.core.experimental.prims import RigidPrim  # 剛体のラッパー


def read_with_fabric():
    """fabric で全部の姿勢を読む。"""
    with backend_utils.use_backend("fabric"):  # fabric を指定する
        xform.get_world_poses()  # 全部の姿勢を読む


print(f"[RESULT] N={CUBE_COUNT} fabric: {time_per_call_us(read_with_fabric, repeat_count=50):.1f} us")  # fabric の結果
rigid = RigidPrim(paths)  # 同じ Cube を剛体のラッパーで受け持つ
print(f"[RESULT] N={CUBE_COUNT} RigidPrim 既定（Play 中なら tensor）: {time_per_call_us(lambda: rigid.get_world_poses(), repeat_count=50):.1f} us")  # tensor の結果
```

### 結果

| N | fabric | RigidPrim（Play 中、tensor） | 参考（fabric / tensor） |
|---|---|---|---|
| 1000 | ＿＿＿ µs | ＿＿＿ µs | 237 µs / 150 µs |

## 5. プリムを1個ずつループで書く

### なぜ重いか

ラッパーのメソッドは、1回の呼び出しごとに、インデックスの解決、入力の配列への変換、バックエンドの選択、view への書き込みをする。
1個ずつ `indices=[i]` で呼ぶと、この固定費がプリムの数だけかかる。

### 重さを確かめるコードと、なくした後を確かめるコード

Script Editor に貼って実行するコード（項目4のコードで Cube を作った後、Play 中に実行する）
```python
# 100個の剛体の位置を、1個ずつ100回書く場合と、まとめて1回で書く場合を比べる
import numpy as np  # 位置の配列を作る

from isaacsim.core.experimental.prims import RigidPrim  # 剛体のラッパー

WRITE_COUNT = 100  # 書く剛体の数
rigid_subset = RigidPrim(paths[:WRITE_COUNT])  # 先頭の WRITE_COUNT 個を受け持つラッパー
targets = np.zeros((WRITE_COUNT, 3), dtype=np.float32)  # 書く位置
targets[:, 2] = 5.0  # 高さ 5 m に置く


def write_one_by_one():
    """1個ずつ WRITE_COUNT 回呼ぶ。"""
    for index in range(WRITE_COUNT):  # 1個ずつ
        rigid_subset.set_world_poses(positions=targets[index : index + 1], indices=[index])  # 1個だけ書く


one_by_one_us = time_per_call_us(write_one_by_one, repeat_count=10)  # 1個ずつの場合
batched_us = time_per_call_us(lambda: rigid_subset.set_world_poses(positions=targets), repeat_count=50)  # まとめて1回の場合
print(f"[RESULT] 1個ずつ{WRITE_COUNT}回: {one_by_one_us:.1f} us、まとめて1回: {batched_us:.1f} us")  # 結果を表示する
```

### 結果

| 条件 | 100 個を書く時間 | 参考 |
|---|---|---|
| 1個ずつ100回 | ＿＿＿ µs | 11499 µs |
| まとめて1回 | ＿＿＿ µs | 89 µs |

### なくす方法

書きたい値を、全部のプリム分の配列（形は（プリムの数, 3）など）にまとめてから、1回の呼び出しで書く。一部のプリムだけを書く場合も、`indices` にまとめて渡して1回で書く。

## 6. 物理の計算結果を毎ステップ USD に書き戻す

### なぜ重いか

GUI の既定では、物理エンジンは毎ステップ、すべての剛体の姿勢と速度を USD の属性に書き戻す（`/physics/updateToUsd` と `/physics/updateVelocitiesToUsd` が true）。USD の属性への書き込みは、剛体1個ずつの処理になるので、剛体の数に比例して時間がかかる。物理の計算そのもの（物理ステップ）は、剛体 1000 個で 1回 0.6 ms しかかからなかったのに、1回の更新は 66 ms かかった。

### 重さを確かめるコード

更新の時間を測るため、メインループの待ち（1秒に60回に合わせる待ち）を一時的に外す。測り終わったら元に戻す。

Script Editor に貼って実行するコード（ファイルではない。項目4のコードで Cube を作った後、Stop 中に実行する）
```python
# Play して120回の更新の時間を測り、終わったら Stop して設定を元に戻す
import asyncio  # async の関数を Kit のイベントループで走らせる
import statistics  # 中央値を計算する
import time  # 高分解能タイマー perf_counter を使う

import carb.settings  # メインループの待ちの設定を変える
import omni.kit.app  # メインループの更新を待つ
import omni.timeline  # Play / Stop を切り替える

UPDATE_COUNT = 120  # 何回分の更新を測るか
settings = carb.settings.get_settings()  # 設定ストア
PACING_KEYS = {  # 待ちを外すために変える設定と、測る間の値
    "/app/player/useFixedTimeStepping": False,  # 固定刻みを外す（目標フレームレートの待ちがなくなる）
    "/app/runLoops/main/rateLimitEnabled": False,  # 上限周波数の待ちを外す
}


async def measure_updates(label: str) -> None:
    """Play して UPDATE_COUNT 回の更新の時間を測る。"""
    saved = {key: settings.get(key) for key in PACING_KEYS}  # 元の値を覚えておく
    for key, value in PACING_KEYS.items():  # 待ちを外す
        settings.set_bool(key, value)  # 設定を変える
    app = omni.kit.app.get_app()  # 更新を待つためのアプリのインスタンス
    timeline = omni.timeline.get_timeline_interface()  # timeline のインスタンス
    timeline.play()  # Play
    for _ in range(20):  # 最初の20回は捨てる（初期化の時間が入るため）
        await app.next_update_async()  # 更新を1回待つ
    durations = []  # 更新1回ごとの時間（秒）
    previous = time.perf_counter()  # 前の更新が終わった時刻
    for _ in range(UPDATE_COUNT):  # UPDATE_COUNT 回の更新を測る
        await app.next_update_async()  # 更新を1回待つ
        now = time.perf_counter()  # 今の時刻
        durations.append(now - previous)  # 更新1回分の時間を記録する
        previous = now  # 次の基準にする
    timeline.stop()  # Stop
    for key, value in saved.items():  # 設定を元に戻す
        settings.set_bool(key, bool(value))  # 元の値を書く
    print(f"[RESULT] {label}: 更新1回の中央値 {statistics.median(durations) * 1000:.2f} ms")  # 結果を表示する


asyncio.ensure_future(measure_updates("USD へ書く（既定）"))  # Kit のイベントループで走らせる（この行はすぐに戻る）
```

### 結果

| 条件 | 更新1回の中央値 | 参考（剛体 1000 個） |
|---|---|---|
| USD へ書く（既定） | ＿＿＿ ms | 66.1 ms |

### なくす方法

Play 中に USD の値を読む必要がなければ、物理の書き出し先を Fabric に変える（Isaac Lab の既定と同じ構成）。
USD も Fabric も読まないなら、どちらにも書かない。どちらの場合も、物理の値は `isaacsim.core.experimental.prims.RigidPrim`（tensor）で読める。
Fabric へ書く構成では、usdrt / fabric のバックエンドでも読める（[pose_freshness_probe](05_pose_freshness_probe.md) の結果の表）。

Script Editor に貼って実行するコード（ファイルではない。Stop 中に、どちらか一方を実行する）
```python
# 物理の書き出し先を変える
import carb.settings  # Kit の設定を読み書きする
from isaacsim.core.simulation_manager import SimulationManager  # 物理の出力先を切り替えるクラス

SimulationManager.enable_fabric(True)  # Fabric へ書き、USD へは書かない（元に戻すときは enable_fabric(False)）

# どちらにも書かない場合は、上の行の代わりに次の2行を実行する
# SimulationManager.enable_fabric(False)  # omni.physx.fabric を無効にする
# [carb.settings.get_settings().set_bool(key, False) for key in ("/physics/updateToUsd", "/physics/updateVelocitiesToUsd", "/physics/updateParticlesToUsd", "/physics/updateForceSensorsToUsd")]  # USD へも書かない
```

### 軽くなったことを確かめる

書き出し先を変えてから、「重さを確かめるコード」の最後の行のラベルを変えて、もう一度実行する。

| 条件 | 更新1回の中央値 | 参考（剛体 1000 個） |
|---|---|---|
| Fabric へ書く | ＿＿＿ ms | 8.4 ms |
| どちらにも書かない | ＿＿＿ ms | 6.2 ms |

`/physics/updateToUsd` だけを false にして速度の書き戻し（`/physics/updateVelocitiesToUsd`）を残すと、29 ms までしか速くならなかった。速度の書き戻しも同じくらい重い。

## 7. GPU の配列を CPU に写す

### なぜ重いと考えたか、実際にはどうか

物理を GPU で計算し、データを GPU に置く構成（`/physics/suppressReadback = true`）では、ラッパーが返す配列も GPU にある。
**`.numpy()` を呼ぶと、GPU から CPU へ写す処理が入る。**

剛体 1000 個の `isaacsim.core.experimental.prims.RigidPrim.get_world_poses()` で測ると、写さなければ 240 µs、`.numpy()` で CPU に写すと 331 µs だった。写す費用は 1000 個で約 90 µs で、項目1・4・5・6に比べて小さい。先頭の1個だけを `indices=[0]` で読んで写すと、387 µs とかえって遅くなった（インデックスを解決する処理が加わるため）。

### 重さを確かめるコードと、なくした後を確かめるコード

Script Editor に貼って実行するコード（ファイルではない。GPU の構成で Play 中に、項目4のコードで Cube を作った後に実行する）
```python
# GPU の配列のまま使う場合と、CPU に写す場合を比べる
import warp as wp  # GPU の処理の完了を待つために使う

from isaacsim.core.experimental.prims import RigidPrim  # 剛体のラッパー

rigid_all = RigidPrim(paths)  # 全部の Cube を受け持つラッパー
positions, _ = rigid_all.get_world_poses()  # 1回読んで、配列の置き場所を確かめる
print(f"[INFO] 配列のデバイス: {positions.device}")  # cuda:0 なら GPU の構成になっている


def read_on_gpu():
    """読んだ配列を GPU のまま使う（完了まで待つ）。"""
    rigid_all.get_world_poses()  # 読む
    wp.synchronize()  # GPU の処理の完了を待つ


print(f"[RESULT] GPU のまま: {time_per_call_us(read_on_gpu):.1f} us")  # 写さない場合
print(f"[RESULT] CPU に写す: {time_per_call_us(lambda: rigid_all.get_world_poses()[0].numpy()):.1f} us")  # 写す場合
```

### 結果

| 条件 | 1回あたり | 参考（剛体 1000 個） |
|---|---|---|
| GPU のまま | ＿＿＿ µs | 255 µs（完了を待った場合） |
| CPU に写す | ＿＿＿ µs | 331 µs |

### GPU の構成にする方法

Script Editor に貼って実行するコード（ファイルではない。Stop 中に実行してから Play する）
```python
# 物理を GPU で計算し、データを GPU に置く構成にする
import carb.settings  # Kit の設定を読み書きする
from isaacsim.core.simulation_manager import SimulationManager  # Physics Scene の設定を変えるクラス

settings = carb.settings.get_settings()  # 設定ストア
settings.set_bool("/physics/suppressReadback", True)  # 結果を CPU に読み戻さない（データを GPU に置く）
settings.set_int("/physics/cudaDevice", 0)  # 使う GPU の番号
SimulationManager.enable_gpu_dynamics(True)  # Physics Scene で GPU の計算を有効にする
SimulationManager.set_broadphase_type("GPU")  # 衝突の候補探しも GPU で行う
```
