1. 外側から内側への6層レイヤー全体像：Isaac Sim はどう積み上がっているか

Isaac Sim を一体の巨大シミュレータとして見ると全体像を見失います。実態は、最内層のマイクロカーネルである Kit カーネル の周囲に、共有メモリ・専門エンジン・ロボティクス拡張が玉ねぎのように重なった6層のモジュラー構造です。外側から内側へ順番に役割を剥がしていくと、各コンポーネントの立ち位置が一目で整理できます。

  • ❶ L5 最外層（アプリ起動・外部連携・UI 層）： ユーザーが直接触れる入口です。isaacsim.exp.full.kit などの Experience 構成ファイル、Python スクリプトから起動する SimulationApp、ROS 2 通信を担う isaacsim.ros2.bridge、および omni.ui ベースの GUI ウィンドウ群が属します。
  • ❷ L4 ロボティクス・合成データ ドメイン層： 「ロボット」「関節」「センサー」「強化学習環境」といった意味論を与える層です。SimulationManager、プリム操作ラッパー isaacsim.core.experimental.prims、軌道生成 isaacsim.robot_motion.cumotion、合成データ生成 omni.replicator.core、ノード計算グラフ omni.graph.core が連携します。
  • ❸ L3 統一抽象・時間・イベント仲介層： 特定の物理エンジン実装への依存を断ち切る「防波堤」です。再生時刻を管理する omni.timeline、物理エンジン共通 VTable を定義する物理抽象インターフェース omni.physics、ステージ更新を中継する omni.physics.stageupdate、GPU 配列ビューを提供する omni.physics.tensors で構成されます。
  • ❹ L2 シーン表現・共有状態ハブ層（USD ＆ Fabric）： 全エンジンが共有する「単一の状態ハブ」です。アセット構造と物理スキーマを保持する永続シーングラフ（USD）（omni.usd）と、実行中の座標・頂点配列を GPU 上で高速中継する 実行時共有メモリ（Fabric / USDRT）USD の木構造トラバーサルや CPU コピーを省き、GPU/CPU 上の連続配列（SoA: Structure of Arrays）として剛体姿勢やメッシュ頂点を保持するランタイムキャッシュ。 （usdrt.scenegraph）の二階建てになっています。
  • ❺ L1 専門計算エンジン層（物理エンジン ＆ RTX 描画）： 重たい数値計算と GPU カーネルを実行する専門職です。物理側には omni.physx（PhysX 5）と isaacsim.physics.newton（Newton / Warp）が並立し、描画側には描画デリゲート（Hydra Scene Delegate）である omni.hydra.usdrt_delegate とレイトレーシング描画エンジン（RTX Renderer）である omni.hydra.rtx が対等にぶら下がります。
  • ❻ L0 最内層（Kit カーネル ＆ Carbonite 基盤）： すべての土台となる C++ マイクロカーネルです。 CarboniteNVIDIA Omniverse の最下層 C++ プラグインSDK。ロギング、設定辞書、イベントディスパッチャ、Fiber タスクスケジューラなど OS 抽象化とプラグイン動的ロードを提供する。 プラグイン群（carb.eventdispatcher、carb.settings、carb.tasking）の上で、拡張機能ローダ omni.ext とアプリ実行ループ omni.kit.app（および Isaac 専用ループ omni.kit.loop-isaac）が心臓の鼓動を刻みます。

2. omni.kit フレームワークの役割と、物理エンジンが介入する4つの接点

もっとも重要な設計上の事実は、Kit カーネル（omni.kit.app）自体は「剛体」も「重力」も「衝突」も一切知らないという点です。omni.kit は純粋なアプリケーション基盤として、(A) 拡張機能の依存解決とロード（omni.ext）、(B) 1フレームごとの更新ループ駆動（preUpdate / update / postUpdate）、(C) イベントバス（carb.eventdispatcher）、(D) 階層設定ツリー（carb.settings）の4機能だけを提供します。

では、物理エンジン（PhysX や Newton）はどうやって omni.kit のフレーム進行に割り込んでいるのでしょうか。介入は以下の4つの接点で行われます。

  • ❶ 接点1：RunLoop の刻み制御と Timeline 購読
    Isaac Sim は標準ループを omni.kit.loop-isaac に差し替え、実時間ではなく決定論的な固定 dt で update イベントを発火させます。omni.timeline がその刻みを受けて再生時刻を進め、omni.physics.stageupdate がステージ更新コールバック（StageUpdateFns.on_update）を呼び出します。
  • ❷ 接点2：omni.physics への関数テーブル（Simulation）登録
    Isaac Sim 6.2.0 では PhysX（omni.physics.physx）も Newton（isaacsim.physics.newton）も、直接 Kit に刺さるのではなく物理抽象インターフェース IPhysics に対して Simulation 構造体（SimulationFns・StageUpdateFns・SceneQueryFns）を登録します。これにより実行時でも SimulationManager.switch_physics_engine("newton") の1行でバックエンドを切り替えられます。
  • ❸ 接点3：USD からの初期パースと Fabric への結果書き戻し
    再生開始時（StageUpdateFns.on_attach）だけ永続シーングラフ（USD）の UsdPhysics.Scene や衝突メッシュをパースして GPU バッファを確保します。毎ステップの計算結果（simulate → fetch_results）は遅い USD 通知を避け、GPU 上の実行時共有メモリ（Fabric / USDRT）へ直接書き出します。
  • ❹ 接点4：Tensor 直接介入と Hydra 描画への非同期引き渡し
    強化学習やロボット制御は isaacsim.simulation.physics_pre_step イベントで介入し、omni.physics.tensors 経由で GPU ソルバー内の関節トルク・状態配列を直接読み書きします。一方、描画デリゲート（Hydra Scene Delegate）である omni.hydra.usdrt_delegate は Fabric 上の更新属性だけを検知して omni.hydra.rtx に渡すため、物理エンジンと描画エンジンは互いの内部コードを一切参照しません。

4. 1フレーム（1 Tick）の中で何がどの順番で起きているか（シーケンス図）

SimulationApp.update()（または GUI 起動時のメインループ 1 周）が呼ばれた瞬間から、物理が解かれ、RTX レイトレーシング画像やセンサー出力が得られるまでの時系列を4フェーズに分けたシーケンス図です。モード切替ボタンで「標準 Timeline 駆動」と「強化学習・手動 Tensor 制御」の注目ポイントを確認できます。

  • ❶ Phase 1（Tick 開始と時間進行）： omni.kit.loop-isaac が固定刻み幅 dt を決定し、preUpdate に続いて update を発火します。omni.timeline が再生中であれば時刻を進め、omni.physics.stageupdate の StageUpdateFns.on_update を呼び出します。
  • ❷ Phase 2（Pre-Step 介入と物理ソルバー実行）： 物理ステップの直前に isaacsim.simulation.physics_pre_step が通知され、ロボット制御器や強化学習方策が omni.physics.tensors 経由で関節目標値や外力を書き込みます。直後にアクティブな物理エンジン（PhysX または Newton）の SimulationFns.simulate と SimulationFns.fetch_results が GPU 上で拘束・衝突・変形を解きます（dt が物理刻みより大きい場合は内部で複数サブステップ反復）。
  • ❸ Phase 3（Fabric 同期と Post-Step 通知）： ソルバー完了後、omni.physx.fabric（または Newton の Fabric Sync）が更新された剛体姿勢（omni:fabric:worldMatrix 等）や変形メッシュの頂点配列（points）を GPU 上の実行時共有メモリ（Fabric / USDRT）へ一括反映します。その後 isaacsim.simulation.physics_post_step が発火し、接触センサーや観測値 Tensor の読み出しが可能になります。
  • ❹ Phase 4（Hydra 差分抽出・RTX 描画・PostUpdate）： レンダリング対象フレームでは、omni.hydra.usdrt_delegate が Fabric 内の変更フラグ（Dirty Bit）だけを読み取って omni.hydra.rtx に渡し、加速構造（TLAS / BLAS）を更新してレイトレーシング描画・RTX センサー計算・Replicator アノテーションを実行します。最後に postUpdate で1フレームが閉じます。
標準 GUI / Timeline 同期実行モード： 毎フレーム update（物理ステップ）と描画（Hydra / RTX）が両方走り、ビューポートとカメラセンサーがリアルタイム更新されます。

5. なぜ USD と Fabric と Tensor の3系統が存在するのか（CPU / GPU データ経路図）

Isaac Sim を深く触り始めると必ずぶつかる疑問が「なぜ同じロボットの姿勢やメッシュに、pxr.Usd・usdrt（Fabric）・omni.physics.tensors の3通りのアクセス経路があるのか？」という点です。答えはCPU メモリと GPU VRAM の境界コストにあります。

  • ❶ 経路A：永続シーングラフ（USD / CPU RAM 主体）
    OpenUSD（pxr.Usd）はレイヤー合成・バリアント切替・ファイル保存に最強ですが、木構造の辞書検索と TfNotice 変更通知が CPU 上で走るため、数千個の剛体や数万頂点の軟体を毎秒60〜120回書き換えると CPU ボトルネックで破綻します。そのため初期化・ステージ構築・停止後のリセット時のみ使われます（/physics/suppressReadback 設定により実行中の CPU 書き戻しは抑止可能です）。
  • ❷ 経路B：物理ソルバー内部バッファ ＆ Tensor API（GPU VRAM 直結）
    物理エンジン（PhysX GPU / Newton）はシミュレーション開始時に専用のアリーナを GPU VRAM 上に確保します。omni.physics.tensors や isaacsim.physics.newton.tensors は、このソルバー内部配列へのゼロコピーポインタを wp.array や torch.Tensor として直接公開するため、数千環境の強化学習でも PCIe 転送ゼロで回ります。
  • ❸ 経路C：実行時共有メモリ（Fabric / USDRT — エンジン間の GPU 掲示板）
    物理エンジン以外のサブシステム（描画エンジンや OmniGraph、カスタム Warp カーネル）に現在の姿勢・変形頂点を渡すための GPU 共有テーブルが usdrt.scenegraph です。ソルバー内部構造を知らなくても、標準属性名（omni:fabric:worldMatrix や points）で VRAM 上のまま読み書きできます。
  • ❹ 経路D：Hydra USDRT Delegate → RTX BVH（GPU 内完結レンダリング）
    /app/useFabricSceneDelegate=true（Isaac Sim 既定）のとき、omni.hydra.usdrt_delegate は CPU USD を経由せず GPU Fabric から直接 RTX のジオメトリバッファを更新します。

6. カスタム DeformableBody を実装するとき、物理エンジンとシェーダーの両方に手を入れるのか？

結論：通常の変形表現（布・ゴム・生体組織・ケーブルなど、メッシュ頂点座標 points の移動で表現できる変形体）であれば、シェーダーに手を入れる必要はありません。
改修が必要なのは「物理計算ソルバー層（Warp / CUDA / C++）」と「Fabric（usdrt）への頂点書き出し・RunLoop 接続層」の2箇所のみです。シェーダー（MDL マテリアル等）に触るのは「応力・温度などで色や質感を動的に変えたい場合」や「三角形メッシュ頂点移動では表せない破断・体積表現をする場合」に限られます。

なぜシェーダーを改造しなくてもカスタム変形体が正しく描画されるのか？

一般的なゲームエンジン（ラスタライザ）で GPU スキニングや独自変形を実装する場合、頂点シェーダー（Vertex Shader）を書き換えて GPU 描画パイプライン内で頂点を動かす設計がよく採られます。しかし Isaac Sim の レイトレーシング描画エンジン（RTX Renderer） は根本的に仕組みが異なります。

  • ❶ 物理ソルバー側の仕事（ここを作る）： 独自 FEM・MPM・XPBD などのカスタム計算カーネル（たとえば NVIDIA Warp カーネル）を書き、四面体格子やプロキシメッシュの節点変位を計算して、描画用 UsdGeom.Mesh の頂点座標配列を計算します。
  • ❷ Fabric 頂点ブリッジの仕事（ここを繋ぐ）： 計算した頂点座標を usdrt.Sdf.ValueTypeNames.Point3fArray 型の points 属性として GPU Fabric 上でインプレース更新します（wp.fabricarray を使えば GPU ポインタを直接書き換えられます）。
  • ❸ Hydra / RTX 側の自動処理（手を入れる必要なし）： レイトレーサーにはラスタライザのような「描画時の頂点シェーダー変形」ではなく、空間加速構造である BLAS Refit（BVH 再フィット）Bottom-Level Acceleration Structure（メッシュ単位の境界ボリューム階層）のトポロジーを保ったまま、移動した頂点座標に合わせてバウンディングボックスを GPU 上で高速更新する処理。 があります。omni.hydra.usdrt_delegate が Fabric の points 変更を検知すると、omni.hydra.rtx が自動で BLAS を再フィットし、既存の MDL サーフェスシェーダーMaterial Definition Language。レイが三角形に衝突した後の反射率・粗さ・屈折（OmniPBR / OmniSurface 等）を記述する物理ベースマテリアル定義。 （OmniPBR や OmniSurface）で影・反射・相互反射まで正確にレンダリングします。
  • ❹ 例外としてシェーダー（MDL）側にも手を入れるケース： 「引っ張られた部分の応力（ミーゼス応力）を赤くヒートマップ表示したい」「伸び率に応じて表面の粗さ（Roughness）や透明度を変えたい」といった場合は、ソルバー側からカスタム頂点属性（primvars:stress や primvars:displayColor）を書き出し、それを受け取る MDL マテリアルグラフ（UsdShade.Shader の Primvar Lookup ノード）を組みます。
