Isaac Sim 1 コマ検証ハンズオン

同梱スクリプト verify_backend_lag_step_by_step.py を手元の Isaac Sim 6.2.0 で動かし、Enter キーで 1 コマずつ止めながら、Viewport の絵とコンソールの数値（USD Stage / Fabric / PhysX / Newton）を直接見比べる実習ガイドです。背景原理の詳細は 解説ページ を参照してください。

準備と起動コマンド

スクリプトは C:\isaacsim-6.2.0\tools\myext\sim_app_launcher.py 経由で必須設定（HUD FPS 表示・自作拡張有効化・UTF-8 コンソール）と omni.physx.fabric・myext.robot.geometric_newton を自動ロードします。

実行モード別のコマンド（PowerShell / コマンドプロンプト）
1.\run_verify.bat
2.\run_verify.bat --exp 2
3.\run_verify.bat --headless --auto

1.\run_verify.bat（既定）：GUI を開き、各コマで Enter 待ちしながら Viewport とコンソールを見比べます。 2--exp 2：実験 1〜4 のうち指定番号だけ実行します。 3--headless --auto：画面なし・自動進行で全アサーションを一括確認します。

実験 1：USD Stage と Fabric のズレを目撃する

.\run_verify.bat --exp 1 を実行します。同じ 1 つの Prim に対して USD Stage と Fabric が別々の値を持つ瞬間を 2 パターン確認します。

1 実験 1-A（動的剛体の重力落下）：omni.physx.fabric 有効状態で Play を押すと、Viewport 上の青い箱 /World/DynamicCube は重力で落下して Fabric Z が 0.8705 m まで下がりますが、USD Stage Z は初期値 1.5000 m のまま 1 ミリも動きません。

2 実験 1-B（ロボットの Fabric のみ更新）：write_target="fabric" で set_dof_positions(q_hit) を呼んだ直後、wrist_1_link は Fabric と USD Stage の間で 1.5602 m もズレた状態になります。

自分の目で確認するチェックポイント
  • 実験 1-A の停止時に Viewport の青い箱が下がっているのに、コンソールの USD Stage Z が 1.5000 のままであること。
  • 実験 1-B で 1 回 app.update() して Viewport のロボットが動いた後も、USD Stage の値は旧姿勢のまま残ること。

実験 2：overlap_shape（1F 遅れ）と ContactReport（2 update 遅れ）

.\run_verify.bat --exp 2 を実行します。同じロボットを 1 コマずつ進めて、PhysX の 2 種類の遅延と「初回だけでなく毎回遅れること」を自分の目で確認します。

1 2-A Frame 0（app.update() 前）：Fabric だけ自己干渉姿勢 q_self へ更新した直後、PhysX overlap_shape は動いていない根元相手の 2/5 組 しか見つけられず、両方大きく動いた upper_arm_link 対 wrist_1..3 の 3 組を見逃します。

2 2-A Frame +1（app.update() 1 回後）と再ジャンプ：app.update() を 1 回呼んで BVH が更新されると 5/5 組 すべて検出されます。さらに元の姿勢へ戻して 2 回目のジャンプを行っても再び Frame 0 = 2/5 組 となり、初回限定ではない定常 1 フレーム遅延であることを確認できます。

3 2-B Frame +1（kinematic ContactReport）：Viewport 上ではロボットが赤い障害物にめり込んで見えるのに、1 回目の衝突検出は移動前位置で走ったため ContactReport penetrating : []（空）になります。

4 2-B Frame +2（app.update() 2 回目）：2 回目の更新でようやく ['forearm_link', 'wrist_1_link', 'wrist_2_link', 'wrist_3_link'] が届きます。

原理の詳細：解説ページ 第 3 層（1F / 2 update / 0F 遅延の因果）

実験 3：Newton の 0 フレーム遅延 & use_fabric="auto" の切り分け

.\run_verify.bat --exp 3 を実行します。Newton が flush_to_usd() も app.update() も挟まずに 0 フレーム遅延で距離まで返すことと、障害物同期の use_fabric="auto" の意味を確かめます。

1 実験 3-A（Newton Frame 0 自己干渉）：write_target="fabric" のまま app.update() 前に 5/5 組すべてと負の separation（最大めり込み -0.02783 m）が返ります。

2 実験 3-B（静的障害物を USD で動かした直後）：Play=ON 中に静的障害物 /World/MovingObstacle を xformOp で手先へ動かした直後（app.update() 前）は Fabric が古いため、use_fabric=True は 0 件 と見逃します。

3 同じ瞬間でも use_fabric='auto' は「静的障害物は USD Stage から読む」と自動判別するため、3 件（最深 -0.12007 m）を 0 フレーム遅延で検出します。

実験 4：GPU 非同期実行（wp.launch）と wp.synchronize_device() の実測

.\run_verify.bat --exp 4 を実行します。GPU 上で 100 万要素 × 400 反復の計算カーネルを投げ、Python へ制御が返るまでの時間と、実際に GPU が計算し終えるまでの時間をストップウォッチで分離して測定します。

1 wp.launch() 自体は GPU キューへ命令を積むだけなので 0.053 ms で即座に Python へ戻ります（この瞬間、GPU はまだ計算途中）。

2 直後の wp.synchronize_device() で実際に GPU 計算が終わるまで 3.171 ms（約 60 倍）待機します。この差こそが、GeometricGpuFabricWriter で同期を外すと書きかけの Fabric を Hydra が読んでしまう直接の証拠です。
