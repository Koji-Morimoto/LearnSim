Isaac Sim バックエンド原理と干渉遅延の仕組み

「Viewport に映っている姿は真の状態なのか」「なぜ overlap_shape は 1 フレーム、ContactReport は 2 フレーム遅れるのか」「なぜ Newton は 0 フレーム遅延なのか」を、下層のメモリ構造から順番に積み上げて解説します。自分の手元で 1 コマずつ確かめる手順は ハンズオン検証ガイド に分離しています。

0. まず押さえる 4 層の前提マップ（Prerequisite）

Isaac Sim の干渉遅延は、結果だけ読むと魔法のように見えます。しかし原因はたった 4 層の前提が下から積み上がっているだけです。

1 第 1 層（データ置き場とメモリ）：Isaac Sim には単一の Source of Truth がなく、姿勢は USD Stage・Fabric・PhysX 内部ワールド・Newton 空間 に分裂しています。

2 第 2 層（フレーム境界と同期）：Fabric への書き込みは即時通知されず、app.update() のフレーム境界で初めて各エンジンへ同期されます。

3 第 3 層（計算順序の差）：PhysX の物理ステップは「接触検知 → 位置更新」の順ですが、幾何モードの Newton は「位置確定 → 接触検知」の順で 1 回で完結します。

4 第 4 層（空間構造と CPU/GPU）：PhysX の Scene Query 用 BVH はフレームをまたいで常駐する CPU 構造であり、Newton は呼び出しのたびに GPU 上で最新配列から即座に判定します。

1. 第 1 層：RAM / VRAM と Fabric・IFabricHierarchy・GPU 同期

1.1 単一の Source of Truth は存在しない

Isaac Sim では、同じ 1 つの Prim（例：/World/UR10e/wrist_1_link）の姿勢がメモリ上の複数箇所に別々のコピーとして存在します。Viewport に映っている絵は「真の状態」ではなく、直前の描画フェーズで Hydra が Fabric を撮影して描いたモニター画面にすぎません。

姿勢の置き場 物理メモリ 本来の役割 主な書き込み元 主な読み取り先
USD Stage（pxr.Usd） RAM（CPU） 設計図・レイヤー合成・ファイル保存のマスタ ユーザー操作、xformOp.Set()、flush_to_usd() XformCache、Usd.Notice 監視者
Fabric（usdrt） RAM / VRAM 2 面キャッシュ 実行中のリアルタイム中継ボード（描画・高速通信） USD→Fabric 同期、PhysX Sync Out、GeometricFabricWriter / GeometricGpuFabricWriter Hydra（Viewport）、PhysX Sync In、sync_environment()
PhysX 内部ワールド（PxScene + BVH） CPU RAM（力学は GPU 選択可） PhysX の力学計算と Scene Query 用空間索引 force_load_physics_from_usd()、Usd.Notice、PhysX ステップ PhysX ソルバ、overlap_shape の相手側、ContactReport
Newton 空間（GeometricScene） VRAM（Warp 配列、CPU も可） 拡張機能専用の幾何計算・衝突判定ワールド newton.eval_fk()、sync_environment() CollisionPipeline.collide()、eval_rigid_contact_kinematics()
なぜ Fabric を更新するのか（Newton や PhysX だけでは画面が動かない理由）： Newton 空間 の配列は純粋な計算メモリであり、画面には映りません。Viewport を動かすには、レンダラ（Hydra）が読む先である Fabric（または USD Stage 経由）へ姿勢を書き込む必要があります。

1.2 属性がバラバラな Prim を SoA で管理する Bucket 構造

1 Fabric は全 Prim を 1 本の配列へ混ぜるのではなく、持っている属性とタグの集合が完全に一致する Prim 同士 を同じ Bucket同一の属性・タグ構成を持つ Prim 群をまとめた表（ECS の Archetype 相当）。属性ごとに連続配列（SoA）で保持する。 にまとめ、内部の索引テーブルで Path -> (Bucket ID, idx) を追跡します。属性を 1 つ追加・削除すると Prim は別の Bucket へ引っ越すため、古い配列ポインタは陳腐化します。

1.3 RAM と VRAM の 2 面キャッシュ（valid ビット管理）

2 「CPU / GPU 共有」とは物理的に 1 つのメモリを共有する意味ではありません。Fabric は各属性配列ごとに RAM 側バッファ と VRAM 側バッファ を遅延確保し、cpuValid / gpuValid の有効ビットでどちらが最新かを管理します。CPU から書けば RAM 側が最新になり GPU 読み取り時に自動転送され、逆に GPU カーネル（wp.fabricarray）で VRAM 側へ直接書けば Hydra が CPU 往復なしでそのまま読めます。

1.4 IFabricHierarchy と「タグ付け時に localMatrix を消す」理由

3 IFabricHierarchy は、親子階層をたどって親からの相対行列 omni:fabric:localMatrix からワールド絶対行列 omni:fabric:worldMatrix を一括展開するエンジンです。両属性とも RAM / VRAM どちらにも乗れ、Kit は毎回の app.update() 描画直前に updateWorldXforms() を自動実行します。

GeometricGpuFabricWriter は Newton が計算済みの omni:fabric:worldMatrix を GPU から直接書くため、初期化時に対象リンクへ Newton ボディ番号のタグ属性を付けると同時に omni:fabric:localMatrix を削除し、IFabricHierarchy が古いローカル行列で上書き・逆算しないように切り離しています。

1.5 wp.synchronize_device() が無いと起きること

4 Warp の wp.launch() は CPU から GPU キューへ注文書を投げるだけの 非同期実行 です。wp.synchronize_device() で GPU 書き込み完了を待たずに戻ると、GPU がリンク姿勢を半分しか書き換えていない途中状態の omni:fabric:worldMatrix を Hydra や後続処理が読み、特定のリンクだけ旧位置に残ってロボットが千切れるデータ競合が起きます。

2. 第 2 層：描画配線・DebugDraw とフレーム境界（Play=OFF / Play=ON）

2.1 Viewport の基本経路は PhysX を通らない

Viewport へ絵を出す基本経路は USD Stage → Fabric → Hydra (FSD) → Viewport であり、PhysX は必須経路ではありません。Timeline の Stop / Play は物理とアニメーションの時間進行スイッチであり、GPU の電源スイッチではないため、Stop 中でも描画と GPU 計算（Warp / Newton）は常時動作します。

Isaac Sim 全体のデータ配線図（5 サブシステム俯瞰） 本質的複雑性のため 5 要素を同時表示・ホバーで周辺ディミング

変更時に Usd.Notice で Fabric の localMatrix へ同期。omni.physx.fabric 有効時は Play 中の PhysX 結果が書き戻されない（無効時は updateToUsd=true で書き戻される）。
2Fabric
write_target="fabric" で直接書込。Hydra が毎フレーム読むランタイム正本。
3PhysX
Play 中の app.update() 時だけ Fabric と Sync In / Sync Out でやり取りする横入りプラグイン。
4DebugDraw
USD Stage にも Fabric にも Prim を作らず、RTX レンダラのオーバーレイ描画リストへ直接座標を積む。
5Hydra (FSD) → Viewport
app.update() の描画フェーズで Fabric の worldMatrix と DebugDraw を合成して 1 枚描く。

2.2 Play=OFF vs Play=ON の 1 フレーム区切り（USD Stage 込み）

GUI アプリでは Kit 本体が暗黙に app.update() を毎秒何十回も回し続け、スタンドアロン（SimulationApp）では Python が app.update() を明示的に呼んだときだけ 1 フレーム進みます。タブで Play=OFF（Stop） と Play=ON の 1 フレーム内部を切り替えて比較できます。

1 フレーム（app.update() 境界）の実行シーケンス
Frame 0（Python 実行中・まだ app.update() を呼んでいない） write_target="fabric"
1 Python → Fabric 新姿勢 T_new を Fabric へ直接書込。USD Stage は初期姿勢のまま、PhysX へも通知は飛ばない（BVH は T_old のまま）。

4 Fabric → Hydra IFabricHierarchy.updateWorldXforms() → Hydra が Fabric＋DebugDraw を読んで Viewport に 1 枚描画（GPU 計算も通常通り利用可能）。

3. 第 3 層：なぜ 1F 遅れ・2 update 遅れ・0F 遅延に分かれるのか

3.1 物理エンジンが「接触 → 位置」の順にならざるを得ない理由

力学シミュレーションの目的は「床や壁を突き抜けさせずに反力で止めること」です。先に現在位置で接触拘束（壁の条件）を見つけないと、ソルバが「壁を突き抜けない速度」を連立して解けません。そのため PhysX の 1 ステップは構造上 ① ステップ開始時の姿勢で接触検知 → ② 力・反力・Kinematic 目標で位置更新 という順序になります。

対して幾何モード（myext.robot.geometric_newton）は反力による押し返しを捨て、① eval_fk() で位置確定 → ② その直後に CollisionPipeline.collide() で接触検知 という「位置 → 接触」の順序を Frame 0 の 1 呼び出し内で完結させます。

app.update() も flush_to_usd() も不要で 5/5 組＋めり込み深さ（[m]）を即取得

3 方式の要点： 1overlap_shape は引数と BVH の参照元が食い違うため 1 フレーム遅れ、 2ContactReport は「移動するフレーム」と「到達後に接触検知するフレーム」が分断されるため 2 update 遅れ、 3Newton はフレーム境界をまたがず「位置 → 接触」を直列実行するため 0 フレーム遅延になります。

3.2 遅延は「初回だけ」ではなく、姿勢を変えるたび毎フレーム定常的に続く

関節角度を毎フレーム q_0 → q_1 → q_2 → q_3 と更新し続けると、Frame k 時点で overlap_shape（Fabric のみ）の相手 BVH は常に q_{k-1}（1 遅れ）、ContactReport は常に q_{k-2}（2 遅れ）になります。テストコードが Stop → Play 直後に 2〜3 回 app.update() を回すのは遅延を消すためではなく、Timeline の Frame Integrity 遷移と初期シーン構築を完了させるウォームアップのためです。

3.3 剛体タイプ（Static / Kinematic / Dynamic）ごとの扱いの違い

USD 設定（種類） PhysX 内部クラス 姿勢の決定者 格納先 BVH と主な制約
Static Collider（CollisionAPI のみ、または rigidBodyEnabled=False） PxRigidStatic ユーザー（USD / Fabric） 静的用 BVH（Static Pruner）。重力で動かず、Static 同士の ContactReport は出ない。
Kinematic RigidBody（kinematicEnabled=True） PxRigidDynamic（eKINEMATIC） ユーザー（setKinematicTarget） 動的用 BVH（Dynamic Pruner）。ContactReport を出せるが 2 update 遅れ、Stop 中は位置同期されない。

4. 第 4 層：overlap_shape が CPU 計算である意味と、Newton の空間構造

NVIDIA PhysX 5 公式仕様として、たとえ物理力学本体を GPU ダイナミクス（enableGPUDynamics=True）で動かしていても、Scene Query（overlap_shape / raycast / sweep）とその空間索引 BVH（Static / Dynamic AABB Tree）は CPU（RAM）側に存在し、Broad / Mid / Narrow の全フェーズが CPU で実行されます。GPU ダイナミクス有効時はステップ終了時（fetchResults()）に最新姿勢が GPU → CPU へ同期（DtoH）されて CPU 側 BVH が更新されます。

比較軸 PhysX（overlap_shape） Newton（CollisionPipeline）
空間構造の持ち方 フレームをまたいで常駐する CPU 上の AABB Tree（BVH） フレームをまたぐ常駐 BVH を持たない（呼び出しのたびに最新 state.body_q から計算）
Broadphase の実体 CPU 上の Static / Dynamic Pruner を探索 512 形状以下は explicit（候補ペア表を GPU 全並列判定）、512 超は sap（GPU 上で毎回 AABB ソート）
計算デバイス Broad / Mid / Narrow すべて CPU eval_fk → Broad → Narrow（GJK/MPR）→ 距離算出まで GPU（Warp）完結
返却情報 ヒットした Prim パス一覧のみ（めり込み深さなし） 符号付き距離 separation（負＝めり込み、正＝クリアランス）、接触点、法線

5. myext.robot.geometric_newton の 1 描画フレームと Play=OFF 性能

myext.robot.geometric_newton では、1 描画フレーム（app.update() 1 周期）の中で姿勢更新・干渉判定・画面反映までを 0 フレームズレで完結させます。また、既定の collision_backend="newton" では Play=OFF でも Play=ON でも PhysX を使わないため force_load_physics_from_usd() は 0 回であり、裏で物理ステップが走らない Play=OFF の方が全体負荷は軽くなります（PhysX バックエンド明示時でもリロードは初回と構造変化時のみ）。

1robot.set_dof_positions(q) # NumPy(単体)または GPU eval_fk → Fabric へ即時書込
2pairs = robot.check_collisions() # GPU Newton 空間で eval_fk → collide → 距離を 0F 確定
3robot.scene.sync_environment() # use_fabric="auto": 動的剛体は Fabric、静的/Stop は USD
4app.update() # Hydra が最新 Fabric と DebugDraw を Viewport へ 1 枚描画

1robot.set_dof_positions(q) で描画用 Fabric を更新し（GPU 直結構成では wp.synchronize_device() で完了保証）、 2robot.check_collisions() が同じフレーム内で干渉とめり込み深さを確定します。 3環境障害物は use_fabric="auto" が「Play 中の動的剛体＝Fabric、静的障害物と Stop 中＝USD Stage」と自動で読み分けるため、どちらの障害物も 0 フレーム遅延で追従します。 4最後に app.update() が 1 回回ると、最新の姿勢と可視化がそのまま 1 枚の絵として描画されます。
