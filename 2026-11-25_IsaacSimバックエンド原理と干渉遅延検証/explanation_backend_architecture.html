Isaac Sim バックエンド原理と干渉遅延の仕組み

Viewport に映っている絵を信じてはいけない理由から出発し、USD Stage・Fabric・PhysX・Newton・Hydra の 5 サブシステムが「どこに何を持ち、どの順序でいつ同期するか」を前提の依存順に解き明かす完全解説です。各バッジにホバーすると図と本文が双方向に連動し、クリックで対応先へ移動します。

0. 全体の地図（なぜ前提を下層から積み上げるのか）

「overlap_shape で 1 フレーム遅れる」「ContactReport で 2 update 遅れる」「Fabric を書いても PhysX に届かない」といった現象は、個別の API リファレンスを断片的に読んでも腹落ちしません。これらすべてが「メモリの分断 → フレーム境界の同期 → 物理ステップ内の計算順序 → 剛体種別と形状近似の制約」という 5 層の前提の上に成り立っているためです。

本解説では、上位の現象をいきなり結論だけ述べるのではなく、最も基礎となる第 1 層から順に積み上げます。

1 第 1 層（メモリ構造と 4 つの姿勢置き場）：Isaac Sim には単一の「真の状態（Source of Truth）」が存在せず、同じロボットの姿勢が USD Stage・Fabric・PhysX 内部ワールド・Newton 空間 の 4 箇所に分裂して保持されます。

2 第 2 層（app.update() とフレーム境界の同期）：Fabric への書き込みは即座に PhysX へ通知されず、app.update() のフレーム境界（および Play=ON / Play=OFF の状態差）を経て初めて各エンジンと Hydra へ伝わります。

3 第 3 層（計算順序の差が生む遅延）：PhysX の物理ステップは「接触検知 → 位置更新」の順で動くのに対し、幾何モードの Newton は「位置確定 → 接触検知」の順を 1 呼び出し内で完結させます。この順序差が 1F / 2 update / 0F の違いを生みます。

4 第 4 層（3 種剛体の定義と 6 組み合わせ）：同じコライダーでも Static Collider（ピンク）・Kinematic RigidBody（黄色）・Dynamic RigidBody（緑） で PhysX 内部の扱いと接触報告条件が根本から異なります。

5 第 5 層（BVH の正体と対応形状・近似精度）：Scene Query 用の BVH は PhysX の CPU メモリ内データであり、さらに実際の干渉境界は convexHull・convexDecomposition・trimesh・sdf などの形状表現とバックエンドごとの制約に左右されます。

1. 第 1 層：RAM / VRAM と Fabric・IFabricHierarchy・GPU 同期

1.1 「単一の Source of Truth」は存在しない

Isaac Sim を理解するうえで最初に捨てなければならない思い込みは、「シーンのどこかに唯一の真の状態があり、画面も物理エンジンもそこを直接見ている」という前提です。実際には、同じ 1 つの Prim（たとえば /World/UR10e/wrist_1_link）の姿勢データであっても、メモリ上の 4 つの異なる置き場 に別々のコピーとして保持されています。

そのため、ある瞬間に「Viewport には腕が障害物に突き刺さって見えているのに、USD Stage から読むとまだ初期位置のまま」「Fabric ではもう移動したのに、PhysX の BVH にはまだ 1 フレーム前の位置が入っている」という食い違いが普通に起きます。Viewport に映っている絵は真の状態そのものではなく、直前の描画フェーズで Hydra が Fabric をスナップショット撮影して描いたモニター映像にすぎません。

Newton 空間 の配列（state.body_q）も PhysX 内部ワールド（PxScene）も、どちらも純粋な計算専用メモリであり、レンダラ（Hydra）はそこを一切見に行きません。計算した姿勢を Viewport に表示するには、Hydra が読む先である Fabric へ姿勢を書き込む必要があります。また、Play 中の動的剛体について omni.physx.fabric が有効（Isaac Sim 標準の Fabric 構成）なときは、PhysX は計算結果を重い USD Stage へ書き戻さず Fabric だけへ出力するため、USD Stage は初期姿勢のまま静止し続けます（omni.physx.fabric 無効かつ /physics/updateToUsd=true の構成のみ USD にも書き戻されます）。

1.2 属性がバラバラな Prim をどうやって SoA で管理しているのか（Bucket 構造）

1 「Fabric はフラットな SoA（Structure of Arrays）配列だ」と聞くと、「メッシュを持つ Prim、関節を持つ Prim、ライトなど属性構成がバラバラな Prim をどうやって 1 本の配列に並べるのか」という疑問が自然に出てきます。

答えは、ゲームエンジンの ECS（Entity Component System）における Archetype と同じ Bucket（バケット）分割 です。Fabric は全 Prim を 1 本の配列に混ぜるのではなく、持っている属性名とタグの集合が完全に一致する Prim 同士 を同じ Bucket同一の属性名・型・タグ構成を持つ Prim 群をまとめたテーブル。各属性が列（連続配列＝SoA）、各 Prim が行（添字 idx）に対応する。 へ自動的にまとめます。各 Bucket の中では属性ごとに隙間なくメモリが連続配置（SoA）され、さらに内部の索引テーブルで Path -> (Bucket ID, idx) を追跡します。

この構造には重要な副作用があります。ある Prim に属性やタグを 1 つでも追加・削除すると、属性集合が変わるため その Prim は別の Bucket へ丸ごと引っ越します。したがって、引っ越し前に取得していた配列ポインタやインデックスは陳腐化するため、属性追加（タグ付け）は初期化フェーズで済ませ、毎フレームの更新ループでは Bucket 構造を変えずに既存の配列要素だけを書き換えるのが定石です。

1.3 「CPU / GPU 共有の高速配列」の実体：RAM と VRAM の 2 面キャッシュ

2 「Fabric は CPU / GPU 共有」という言い回しは誤解を招きやすく、PC の物理ハードウェア上でメインメモリ（CPU RAM）とビデオメモリ（GPU VRAM）が 1 つに融合しているわけではありません。実際の仕組みは RAM 側バッファと VRAM 側バッファの 2 面キャッシュ（遅延確保＋valid ビット管理） です。

Fabric 内の各属性配列は、初期状態ではまだ使われていない側のメモリを確保しません。CPU 側から書き込みが起きると RAM 側バッファを確保して書き、cpuValid を true、gpuValid を false にします。その後、GPU 側（Hydra や Warp カーネル）が読もうとした瞬間に gpuValid が false であることを検知し、そのとき初めて RAM → VRAM（HtoD）転送を自動実行して gpuValid を true にします。

逆に、Warp の wp.fabricarray を使って GPU カーネルから omni:fabric:worldMatrix を VRAM 側へ直接書き込んだ場合は、gpuValid だけが true になります。続く描画で Hydra（GPU 上で動作）が読むときにはすでに VRAM に最新値があるため、CPU RAM への往復コピーを 1 回も発生させずにそのまま描画できる のが Fabric GPU 直結の最大の利点です。

1.4 IFabricHierarchy と「タグ付け時に localMatrix を消す」理由

3 USD の階層（親 → 子 → 孫）では、各 Prim が「親からの相対姿勢」を持っています。IFabricHierarchy は、Fabric 内の親子関係グラフをたどり、親からの相対行列である omni:fabric:localMatrix をルートから末端へ掛け合わせて、ワールド絶対行列 omni:fabric:worldMatrix を一括計算する階層変換エンジンです。

ここでよく誤解される点として、omni:fabric:localMatrix は RAM 専用ではなく、omni:fabric:worldMatrix と同じく Fabric の 2 面キャッシュ管理対象（RAM / VRAM 両対応） です。IFabricHierarchy 自体にも CPU 実行版と GPU 実行版があり、Kit は 毎回の app.update() の描画直前（Play=ON/OFF 問わず） に updateWorldXforms() を自動呼び出しして、変更された omni:fabric:localMatrix から omni:fabric:worldMatrix を最新化します。

ところが、myext.robot.geometric_newton の GPU ライタ（GeometricGpuFabricWriter）は、newton.eval_fk() が計算し終えたワールド絶対姿勢を omni:fabric:worldMatrix へ GPU から直接書き込みます。もしその Prim に古い omni:fabric:localMatrix が残っていると、次の描画直前の updateWorldXforms() や親 Prim の更新で 古いローカル行列からワールド行列が上書きされたり、逆に worldMatrix から localMatrix を逆算する余計な処理が走ったりして衝突する おそれがあります。そのため初期化時に、対象リンク Prim へ Newton ボディ番号のタグ属性を付与する（＝全ロボットリンクを 1 つの Bucket へ集める）のと同時に omni:fabric:localMatrix を意図的に削除し、親子階層伝播からきれいに切り離しているのです。

1.5 CPU–GPU 間の非同期通信と wp.synchronize_device() の役割

4 GPU 計算ライブラリである Warp（CUDA）では、Python（CPU）から wp.launch() を呼んでも、CPU は計算が終わるのを待ちません。CPU が GPU のコマンドキューへ「このカーネルをあとで実行して」という注文書を 0.05 ms ほどで投入した瞬間に、Python へ制御を即返却します（非同期実行）。実際の GPU 計算と VRAM 書き込み（たとえば数 ms）は、CPU が次の行を実行している裏側で並列に進行します。

もしこの完了を待たずに次の処理（別の CUDA ストリームで動く Hydra の描画読み取りや、CPU 側への結果読み戻し）へ進んでしまうと、「リンク 0〜2 は新しい姿勢に書き換わったが、リンク 3〜5 はまだ古い姿勢のまま」という中途半端な状態の omni:fabric:worldMatrix を描画してロボットが空中で千切れる、あるいは前のフレームの衝突結果を誤読するといったデータ競合（Race Condition）が起きます。wp.synchronize_device() は、その GPU キューに積まれたすべてのカーネル実行と VRAM 書き込みが完全に終わるまで CPU を一旦停止させる同期バリアです。

2. 第 2 層：app.update() の正体・描画配線とシーケンス図

2.1 「update」「フレーム」「物理ステップ」の 3 概念を切り分ける

議論が混乱しやすい最大の原因のひとつは、「フレーム」という言葉が 3 つの異なる周期を指して混用されることです。本解説では用語を厳密に区別します。

用語 実体（何の 1 周期か） 誰が呼ぶのか Play=OFF（Stop）時の挙動
app.update()（アプリフレーム / 描画フレーム） Kit エンジン全体のメインループ 1 回転（pre_update → update → post_update → render）。 GUI 版では Kit 本体が暗黙に毎秒数十回ループ呼出。スタンドアロン（SimulationApp）では Python スクリプトが明示的に app.update() を呼んだときだけ 1 回進む。 通常通り実行される（UI 更新・USD 通知処理・IFabricHierarchy・Hydra 描画は止まらない）。
物理ステップ（PhysX simulate） PhysX 内部の 1 刻みの力学計算（simulate(dt) → fetchResults()）。 Play=ON のとき、app.update() の update フェーズから Timeline 経由で自動呼出（既定 60 Hz）。物理 120 Hz・描画 60 Hz なら 1 回の app.update() の中で 2 サブステップ走る。 完全にスキップされる（update_simulation() を手動で呼ばない限り 0 回）。

2.2 app.update() 1 回の内部 4 フェーズ（シーケンス図）

app.update() はブラックボックスではなく、内部で明確に 4 つのイベントストリーム を順番に発火させます。各種拡張機能（omni.timeline・omni.physx・usdrt・omni.hydra・omni.debugdraw）はそれぞれのフェーズにコールバックを登録しており、その発火順がそのまま「何がいつ同期されるか」を決めています。

シーケンス図 1：app.update() 1 回（1 描画フレーム）の内部 4 フェーズ 番号バッジ・図中フェーズ帯にホバー／クリックで連動

1pre_update で入力・USD 変更を吸い上げ、 2update で（Play=ON のときだけ）Timeline と PhysX の Sync In → simulate → Sync Out を実行し、 3post_update で IFabricHierarchy.updateWorldXforms() が全 Prim のワールド行列を確定させ、 4render で Hydra (FSD) が Fabric と DebugDraw を合成して 1 枚出力します。

2.3 描画の基本経路は PhysX を通らない（＋ DebugDraw の別レーン）

シーケンス図 1 を見ると、2 つの重要な事実が一目で分かります。

  • Viewport 描画の本線は USD Stage → Fabric → Hydra (FSD) → Viewport であり、PhysX は必須ではない。
    PhysX は Play=ON のあいだだけ Fabric に対して横から Sync In / Sync Out で割り込むプラグインにすぎません。Stop 中に画面が動くのは「PhysX が書き戻しているから」ではなく、USD またはスクリプトが Fabric を更新し、フェーズ 3・4 の Hydra がそれを描いているからです。
  • write_target="fabric"（Fabric バックエンド指定）の意味：
    重い USD Stage の変更通知やレイヤー合成をバイパスし、Fabric へ直接姿勢を書いて Viewport の見た目だけを最速で更新することを意味します。当然ながら、Frame 0 で Fabric を書き換えた直後の瞬間には PhysX へ通知が飛ばないため、「見た目（Fabric）だけ動いたのに PhysX 側のコリジョン状態は古いまま」 という現象が起きます。Fabric → PhysX の経路自体は存在しますが、それは「次の app.update()（Frame 1）の Sync In」という フレーム境界を 1 回またいだタイミング でしか発火しません。
  • DebugDraw の正体：
    線分・点群・球などを描く isaacsim.util.debug_draw / omni.debugdraw は、USD Prim も Fabric Prim も一切作りません。また、呼び出した瞬間にすぐ Hydra を強制描画するわけでもありません。RTX レンダラ（omni.hydra.rtx / omni.kit.renderer.core）が内部に持つ軽量なオーバーレイ描画バッファへ 3D 頂点リストを積み、次の app.update() の render フェーズで本線の 3D 描画の上に重ねて描きます。そのためシーングラフ同期の負荷がなく超高速に描画できます。
シーケンス図 2：Frame 0 → Frame 1 → Frame 2 のデータフロー比較（USD 込み）

Play=ON の要点： 1Frame 0 の Fabric 書込では PhysX の BVH がまだ旧位置（T_old）のまま、 2Frame 1 で初めて Sync In とステップが走り BVH が更新され、 3Frame 1 完了時点で overlap_shape が追いつき、 4Frame 2 のステップで初めて ContactReport が到達します。

3. 第 3 層：なぜ「接触 → 位置」の順なのか、そして 1F / 2 update / 0F 遅延の正体

3.1 物理エンジンが「接触判定 → ソルバ → 位置更新」にならざるを得ない理由

「先に新しい位置を計算してから接触判定すればズレないのでは？」という疑問は極めて自然ですが、力学物理エンジン（PhysX）では構造上その順番にできません。力学シミュレーションの目的は「物体が床や壁を突き抜けないように、接触点に反力（拘束）を発生させて止めること」だからです。

もし先に重力だけで位置を進めてしまうと、物体は床の奥へめり込んだ状態になってしまいます。めり込まない速度をソルバ（連立拘束方程式）で解くためには、ステップ開始時点の位置（T_old）で先に「今どこに壁や床があるか」という接触拘束（Contact）を列挙し、その拘束条件をソルバへ渡してから、最後に速度を積分して新位置（T_new）へ進める 必要があります。

3.2 なぜ Kinematic 剛体の位置更新も「接触判定の後」に来るのか

さらに重要なのが、外部から姿勢を指定する Kinematic 剛体（黄色） の扱いです。「重力で動かないのだから接触判定の前に瞬間移動させてしまえばよいのでは？」と思えますが、PhysX はあえてそうしません。

Kinematic 剛体には「目の前にある箱（Dynamic 剛体）を物理的に押し出す」という役割があるためです。PhysX は setKinematicTarget(T_new) を受け取ると、その Kinematic 剛体を瞬間移動させるのではなく、「質量無限大・速度 v = (T_new - T_old) / dt で移動しようとしている剛体」 としてソルバへ投入します。

  1. ステップ開始時は まだ T_old にいる 状態で接触判定を行い、前方にいる動的剛体との接触拘束を張る。
  2. ソルバ内で、Kinematic 剛体は質量無限大ゆえに一切跳ね返されず、相手側の動的剛体だけを速度 v で押し退ける。
  3. ステップ終端の積分フェーズで、Kinematic 剛体もようやく T_new へ到達する。

もし接触判定より先に T_new へ瞬間移動させてしまうと、薄い壁や小さな動的剛体を通り抜ける（トンネリング）か、深いめり込みから爆散してしまいます。つまり、Kinematic 剛体が「接触判定の後」に位置更新されるのは、すべてを押しのける無限大質量剛体としてソルバの速度拘束に参加させるための物理的必然 なのです。そしてこの設計の副作用として、Kinematic 剛体が T_new に到達した後の接触が検知されるのは「次のステップ（Frame 2）」に持ち越されます。

3.3 「描画後に次の描画直前で届くなら、それは本当に遅れなのか？」（2 つの視点）

ContactReport について、「Frame 1 の最後で T_new が描画され、その見た目に対応する ContactReport が Frame 2 の描画直前（update フェーズ）に届くなら、遅れと呼ぶべきか？」という問いは非常に鋭いポイントです。これは何を起点（t = 0）とみなすかで 2 つの捉え方があります。

  • 視点 A（指令起点：Python が set_dof_positions(q) を呼んだ瞬間＝Frame 0 基準）：
    指令を出してから報告が手元に来るまでに app.update() を 2 回回す必要があるため、「2 update 遅れ」 になります。軌道計画や干渉回避ループのように「今の q が安全か即座に判定して次の指令を決めたい」用途では致命的な遅延になります。
  • 視点 B（描画起点：Viewport に T_new が最初に映る Frame 1 の絵を基準）：
    Frame 1 の絵を描く render フェーズの時点では、まだ ContactReport が空のままです。したがって、「ぶつかった瞬間の Frame 1 の画面に、赤い干渉マーカーや警告 HUD を同時に描画する」ことが構造上できません（マーカーが灯るのは 1 コマ後の Frame 2）。この意味では描画基準で見ても 1 描画フレーム遅れ と言えます。

3.4 遅延は「初回だけ」ではなく、姿勢を変えるたび毎フレーム定常的に続く

よくある誤解に「最初の 1〜2 ステップだけ遅れて、その後は追いつくのではないか？」というものがあります。答えは いいえ（定常的なパイプライン遅延） です。ロボットが毎フレーム q_0 → q_1 → q_2 → q_3 と動き続ける限り、Frame k の時点で overlap_shape（Fabric のみ書込）の相手側 BVH は常に 1 コマ前の q_{k-1}、ContactReport は常に 2 コマ前の q_{k-2} の結果を返し続けます（止まったときだけ 1〜2 フレーム後に追いつきます）。

なお、テストスクリプトが Stop → Play 直後に 2〜3 回 app.update() を空回しするのは「遅延を消すため」ではありません。omni.timeline の Frame Integrity 仕様（play() を呼んだ直後の最初の 1 フレームは状態遷移の整合に使われ、まだ物理ステップが本稼働しないことがある）と、初期シーンの PhysX ロード・ウォームアップを完了させてから測定を始めるためです。

4. 第 4 層：3 種類の剛体／コライダー定義（可視化色＋USD 属性）と 6 組み合わせマトリクス

4.1 3 種類の厳密な定義と Isaac Sim 可視化色（ピンク・黄色・緑）

Isaac Sim の Viewport メニュー（Show by Type → Physics → Colliders）でコリジョン形状を可視化すると、物体の物理種別に応じてワイヤーフレームの色が変わります。用語の取り違えを防ぐため、3 種類の正式定義・Viewport の可視化色・対応する USD スキーマと属性を 1 対 1 で固定します。

用語の取り違え注意（「動的剛体」と「キネマティック剛体」）：
日本語で「動くコライダー」を感覚的に「動的剛体」と呼んでしまうことがありますが、USD / PhysX 公式用語では 重力・反力で物理エンジンが動かす物体だけが「動的剛体（Dynamic RigidBody＝緑）」 であり、スクリプトやアニメーションで外部から位置を指令する物体は 「キネマティック剛体（Kinematic RigidBody＝黄色）」 です。さらに、UsdPhysics.RigidBodyAPI を持たずに xformOp:rotate 等で動かすロボットリンクは、動いていても 「静的コライダー（Static Collider＝ピンク）」 に分類されます。

① 静的コライダー（Static Collider） ピンク / マゼンタ

PhysX 内部クラス：PxRigidStatic（Static Pruner BVH）
姿勢の決定者：ユーザー（USD / Fabric）
USD 判定条件：UsdPhysics.CollisionAPI が付いており、自身にも祖先にも UsdPhysics.RigidBodyAPI がない（または physics:rigidBodyEnabled = False）。
UsdPhysics.CollisionAPI.Apply(prim) # RigidBodyAPI なし # （ある場合は physics:rigidBodyEnabled = False）
「静的」とは「動かない」という意味ではなく「剛体として力学計算されない」という意味。床・壁・治具のほか、RigidBody なしで回転させる幾何ロボットも該当。

② キネマティック剛体（Kinematic RigidBody） 黄色（イエロー）

PhysX 内部クラス：PxRigidDynamic（eKINEMATIC / Dynamic Pruner BVH）
姿勢の決定者：ユーザー（setKinematicTarget）
USD 判定条件：UsdPhysics.RigidBodyAPI ＋ CollisionAPI を持ち、physics:rigidBodyEnabled = True かつ physics:kinematicEnabled = True。
UsdPhysics.CollisionAPI.Apply(prim) rb = UsdPhysics.RigidBodyAPI.Apply(prim) rb.CreateRigidBodyEnabledAttr(True) rb.CreateKinematicEnabledAttr(True)
重力や反力では動かないが、ソルバ内では無限大質量の移動物体として動的剛体を押しのけられる。ContactReport を出せるが、Stop 中は app.update() だけでは位置同期されない。

③ 動的剛体（Dynamic RigidBody） 緑（グリーン）

PhysX 内部クラス：PxRigidDynamic（Dynamic Pruner BVH）
姿勢の決定者：PhysX ソルバ（重力・外力・衝突反力）
USD 判定条件：UsdPhysics.RigidBodyAPI ＋ CollisionAPI を持ち、physics:rigidBodyEnabled = True かつ physics:kinematicEnabled = False（既定値）。
UsdPhysics.CollisionAPI.Apply(prim) rb = UsdPhysics.RigidBodyAPI.Apply(prim) rb.CreateRigidBodyEnabledAttr(True) rb.CreateKinematicEnabledAttr(False) # 既定
毎物理ステップで PhysX が新姿勢を計算し、Sync Out で Fabric へ書き出す。衝突すると反力で押し離される（depenetration）。

※ 可視化色の出典補足：同梱公式ドキュメント（omni.physx.ui/docs/dev_guide/collision_debug_vis.rst）では Dynamic＝Green（緑）、Static＝Magenta（ピンク／マゼンタ）、さらに非対応メッシュ等が convexHull へ自動フォールバックした警告状態が 暗赤（Dark Red） と明記されています。実機の Isaac Sim Viewport 表示では、これらに加えて Kinematic 剛体が黄色（イエロー）として区別表示されます（OmniPVD 再生ビューのみ別配色で Kinematic＝薄青）。

5. 第 5 層：BVH の正体・CPU/GPU 差・バックエンド別の対応形状と精度

5.1 BVH は Fabric ではなく PhysX（CPU RAM）内の純粋な計算用データ構造

BVH（Bounding Volume Hierarchy / AABB 木）は Fabric の中にあるデータではありません。PhysX 内部ワールド (PxScene) が CPU RAM 上に保持している、空間検索専用の純粋なメモリ内データ構造（Static Pruner と Dynamic Pruner の 2 本の木）です。

また、NVIDIA PhysX 5 公式仕様として、たとえ力学ソルバ本体を GPU ダイナミクス（enableGPUDynamics=True）で実行していても、Scene Query（overlap_shape / raycast / sweep）の Broadphase・Midphase・Narrowphase はすべて CPU で実行されます。GPU ダイナミクス有効時は、ステップ終了時（fetchResults()）に GPU から CPU へ最新姿勢がコピー（DtoH）され、CPU 側の BVH が更新されます。

ここで切り分けておくべき重要な原理は、「データが CPU RAM にあるか GPU VRAM にあるか」は計算スループットや転送コストの問題であり、フレーム遅延（1F / 2 update 遅れ）の直接原因ではない という点です。たとえ BVH が GPU VRAM にあったとしても、「次の app.update() まで同期されない」「接触判定の後に位置更新する」という同期タイミングと計算順序が変わらなければ、フレーム遅延はまったく同じように発生します。

5.3 微妙な接近境界（±数 mm）で 3 方式の結果はどこまで一致するか

「同じシーン状態で遅延分だけ 3 ステップ進めたあと、Newton の CollisionPipeline・PhysX overlap_shape・PhysX ContactReport の結果が完全一致するか？」については、確実に一致する範囲 と ±数 mm のかすめ境界で結果が割れうる 3 要因 を明確に切り分けておく必要があります。

  • 実測で一致を確認済み：UR10e の明確な貫通状態（めり込み約 2.8 cm）では、遅延を吸収した後の overlap_shape（5/5 組）と Newton（5/5 組）が完全一致します。また、一様スケールの解析形状（Capsule・Box）では、PhysX の overlap_shape と ContactReport の境界誤差はいずれも真値に対して 3 µm 未満で一致することが確認されています（t15）。
  • ±数 mm のかすめ境界で割れうる 3 要因（同じ姿勢で 3 方式を同時比較するときに必ず揃えるべき条件）：
    1. 距離マージン（オフセット）の差：overlap_shape は純粋な 0 mm 幾何貫通のみヒット、ContactReport（threshold=0）は 2 形状の contactOffset の和（既定では数 mm〜数 cm）より近いと貫通前でも報告、Newton は contact_gap（既定 0 または指定クリアランス）で判定します。比較時は separation <= 0 で揃える必要があります。
    2. 凸包クッキングの実装差：UsdGeom.Mesh を使う場合、PhysX の omni.physx は約 62 頂点・64 面で頭打ちになるのに対し、Newton の compute_convex_hull() は独自の凸包生成を行うため、曲率のあるメッシュの境界では mm 単位の差が出ます。
    3. 動的剛体の押し返し（depenetration）：3 ステップ進めると動的剛体を含むペアは PhysX が反力で押し離してしまうため、ステップ後の overlap_shape だけ非ヒットに転じます。

6. myext.robot.geometric_newton の 1 描画フレームと Play=OFF 性能

ここまでの第 1〜5 層を踏まえると、myext.robot.geometric_newton が 1 描画フレーム（app.update() 1 周期）の中で何をして 0 フレーム遅延と高速描画を両立しているかが完全に一本の線で繋がります。

なお、既定の collision_backend="newton" では Play=OFF でも Play=ON でも PhysX を使わないため、force_load_physics_from_usd() は 1 回も呼ばれません。そのため裏で PhysX ステップが走らない Play=OFF の方が全体負荷は軽く、かつ GPU（Warp / Newton）と Viewport 描画はフルに動作します（PhysX バックエンドを明示指定した場合でも、force_load_physics_from_usd() が走るのは初回およびコライダー構造が変わったときだけで、毎フレーム再ロードするわけではありません）。

1robot.set_dof_positions(q) # FK 計算 → Fabric（VRAM/RAM）へ即時書込（GPU直結時は同期保証）
2robot.scene.sync_environment() # use_fabric="auto": Play中の動的剛体はFabric、静的/StopはUSD
3pairs = robot.check_collisions() # GPU Newton 空間で eval_fk → collide → separation を 0F 確定
4app.update() # Hydra が最新 Fabric と DebugDraw を Viewport へ 1 枚描画

1robot.set_dof_positions(q) で描画用 Fabric を更新します（単体ロボットは NumPy FK → Fabric、大規模バッチや GPU 直結構成では GPU eval_fk → wp.fabricarray 書込＋wp.synchronize_device() で完了保証）。

2robot.scene.sync_environment() では、use_fabric="auto" が「Play 中の動的剛体＝PhysX が書き出す Fabric」「静的障害物や Stop 中＝ユーザー変更が入る USD Stage」を自動で読み分けるため、どちらの環境障害物が動いても 0 フレーム遅延で Newton 空間へ取り込めます。

3robot.check_collisions() が、同じ Frame 0 の中で「位置確定 → 接触検知」を直列に完結させ、衝突ペアと符号付き距離 separation を即座に返します（可視化したい場合はここで DebugDraw へ積みます）。

4最後に app.update() が 1 回回ると、最新のロボット姿勢（Fabric）と最新の干渉マーカー（DebugDraw）が ズレ 0 の 1 枚の絵として同時に Viewport へ描画 されます。
